**пять планов** (§1 разрезан надвое):

1. **Лимиты тарифа** — `docs/superpowers/plans/2026-08-08-platform-plan-limits.md`, **PR #143 в main
   `a04c539c`**. Закрыт.
2. **Фичи** — каталог, лестница разрешений, исключения на клуб, отдача клубским приложениям,
   скрытие выключенных разделов в интерфейсах. НЕ начат.
3. **Роли платформы в базу** — роли = именованные наборы прав в БД, названия прав остаются в коде.
   НЕ начат.
4. **Анонсы платформы** — полоса в Операторе + экран истории + письмо владельцу. НЕ начат.
5. **Офбординг клуба** — срок, выгрузка ZIP/CSV, стирание личного с сохранением финансового.
   НЕ начат.

## Решения волны (durable)

- **Лестница разрешений одна:** ручное исключение для клуба → тариф → умолчание фичи. В панели
  видно, **чем именно решено** («не куплено» и «не выкачено» — разные ответы клиенту).
- **Каталоги объявлены в коде, живут в базе, редактируются в панели** (как
  `BillingPlanSeedHostedService`). Только-база порождает флаги-призраки и молча выключенные фичи,
  которых не ловит ни один тест.
- **Связка «право» vs «роль»:** названия прав обязаны быть в коде (эндпоинты на них ссылаются);
  в данные переезжают роли. Предохранители: нельзя выдать больше, чем есть у тебя;
  `ManagePlatformAdmins` нельзя добавить/отнять себе; последний полный админ неприкосновенен;
  права считаются по текущему составу роли, а не по слепку на момент входа.
- **Анонс:** отметка прочтения на **сотрудника**, не на клуб (иначе первый закрывший полосу
  скроет её у всех). Письмо ровно один раз при публикации. Текст — одно поле, машинного перевода
  на en/tg нет осознанно.
- **Офбординг:** авто-стирания по таймеру нет, срок только показывает «пора». Стираем личное,
  оставляем финансовое; финальный статус `purged` отдельно от `deletion_pending`. Тест обязан
  проверять **обе стороны** — и что личное исчезло, и что финансовое уцелело.

## Durable-уроки плана 1

- **Лимиты были чистой полу-имплементацией:** `LimitsJson` + экран в панели + ноль читателей.
  Теперь единственные точки решения — `OrganizationLimitsJson` (разбор) и `IPlanLimitGuard`
  (решение), четыре точки роста зовут их.
- **«Стоп на рост, старое живёт»:** `current >= limit` перед добавлением, а не «превышено ли сейчас».
- **Второго филиала в продукте не существовало** — ни кнопки, ни эндпоинта, филиал появлялся только
  вместе с организацией. Лимит филиалов проверял бы невозможное, поэтому в план добавлен
  `POST /api/platform/organizations/{id}/branches`. Мёртвая проверка = ложно-зелёное «сделано».
- **Правило должно держаться на ВСЁМ пути.** Дважды за план числа отказа терялись при мэппинге:
  путь старта сеанса из брони (`ReservationSessionStartResult`) и — осознанно отложено — эндпоинт
  привязки устройства. Проверять надо каждый путь до тела HTTP-ответа, а не первый попавшийся.
- **Двойной счёт на границе:** приём приглашения считал само принимаемое приглашение как занятое
  место → при лимите N последнее приглашение принять было нельзя. Лечится
  `CheckStaffUserAsync(..., excludingInviteId)`. Граничных тестов «ровно N» не было ни у кого —
  ошибку поднял сам исполнитель как сомнение.
- **Ложное объяснение отказа хуже отказа:** занятый slug проверяется ДО лимита; неизвестная
  организация не отказывается «по лимиту» (guard возвращает `null`, за «нет такой» отвечает
  вызывающий).
- **Отказ несёт числа:** код `plan_limit_reached` + предел/текущее/тариф; фраза собирается клиентом.
  В Операторе точка расширения — `projectOperatorError` в `src/apiErrors.ts` (таблица код→ключ);
  для чисел ей понадобился проброс значений в `t()`.

## Открытые хвосты

- Отложенные миноры плана 1: эндпоинт привязки устройства не отдаёт числа наружу; мёртвый
  `InMemoryDeviceEnrollmentService` без проверки лимита; гонка по slug без маппинга
  `DbUpdateException` в 409 (тот же пробел у создания организации — чинить одним патчем);
  generic-тост поверх конкретной причины в `NewBranchDialog`; опечатка «едят» в комментарии
  `PlanLimitExceededDto`.
- **Флак Оператора, не связанный с веткой:** `App under an active support session > renders the real
  operator shell` падает в полном прогоне и на `main`, в одиночку проходит — протечка между тестами
  (см. [[frontends-on-bun-test]] про `mock.module`).
- Прогон бэкенда с настоящим Postgres требует **четырёх** переменных, не одной:
  `AFK4_PLATFORM_ADMIN_…`, `AFK4_RESERVATION_…`, `AFK4_POS_POSTGRES_TEST_CONNECTION_STRING`,
  `AFK4_COMMERCE_TEST_POSTGRES` (+ `AFK4_REQUIRE_POSTGRES_TESTS=1`). С одной остаются skip и одно
  падение.
- Ветка плана делалась от `main`, но **коммиты спеки и плана не были запушены в origin** — они
  уехали внутрь squash-мержа, и локальный `main` разошёлся с удалённым. Лечится
  `git reset --hard origin/main` после проверки, что документы совпадают.
