Волна C эпика [[platform-admin-directory-2fa]] спроектирована целиком одной спекой
`docs/superpowers/specs/2026-08-07-platform-observability-and-analytics-design.md`, реализуется
тремя планами — **все три в main: план 1 (§0 инциденты, §1 здоровье, §4 оповещения) PR #140
`b4100a8f`; план 2 (§2 бизнес-аналитика) PR #141 `1d48ea33`; план 3 (§3 история клуба) PR #142
`9df9bc58`. Волна C закрыта целиком.** Волна D (продуктовые операции) не проектировалась.

## Что теперь есть

- `platform_job_runs` — прогон каждого периодического задания; пишет **общая обёртка**
  `PlatformPeriodicJob` (шесть заданий переведены на неё). Архитектурный тест
  `PeriodicJobRegistrationTests` не даст завести седьмое в обход наблюдения; белый список — только
  одноразовые сервисы старта.
- `platform_incidents` — проблема с дедупликацией; инвариант «один открытый инцидент на ключ»
  держит **частичный уникальный индекс** `IX_platform_incidents_DedupKey` с фильтром
  `"ResolvedAtUtc" IS NULL`.
- `PlatformHealthWatchJob` (5 мин) + чистая функция `PlatformHealthRules`; `PlatformJobIntervalCatalog` —
  единственный источник интервалов для сторожа и экрана.
- `PlatformAlertNotifier` — письма и SMS; экран «Здоровье» под правом `platform.health.view`
  (обе роли платформы).

### План 2 (аналитика)

- Выручка по месяцам — **из выставленных счетов** (`MonthlyRevenue.Spread`), не накапливается: у счёта
  есть вид, период и сумма, поэтому цифра не может разойтись с биллингом. Остаток от неделящейся
  суммы раскладывается так, что сумма частей ТОЧНО равна сумме счёта; `void` исключается;
  кредит-нота (`InvoiceKindNames.Credit`, отрицательная сумма) уменьшает свой месяц.
- Приход/отток — **только из `subscription_daily_snapshots`** (`SubscriptionMovement.Compute`):
  состояние подписки счетами не восстановить. Платящий = `active` или `past_due` (долг ≠ уход).
- `EfSubscriptionSnapshotRunner` пишет ВЧЕРАШНИЙ день, бэкфиллит от последней известной даты
  КАЖДОЙ организации (не от фиксированного окна — иначе новая организация получает выдуманную
  историю), потолок `MaxBackfillDays = 30`. Идемпотентность — уникальный индекс (организация, дата).
- Экран — **четвёртая вкладка раздела «Деньги»**, не новый пункт рейла; право то же
  `platform.billing.view`. Графики на `recharts` (была в зависимостях панели, но нигде не
  использовалась — этот экран первый).

### План 3 (история клуба)

- `branch_daily_snapshots` (филиал, дата) — сеансы, выручка, открытия смен, связь. Пишет ОТДЕЛЬНОЕ
  задание `branch_snapshots` (не довесок к снимкам подписок, вопреки букве спеки): одно задание =
  одна запись прогона = одна причина отказа, иначе падение клубной свёртки экран здоровья объявил бы
  провалом снимков подписок. Седьмое наблюдаемое задание встало без правок — `Watched` и
  `PlatformJobIntervalCatalog` нигде не хардкодят количество.
- **`AgentAlive` трёхзначен (`bool?`)**: `true`/`false`/**`null` = «нет данных о связи»**. Живость
  меряется только «сейчас» (heartbeat перезаписывается), поэтому доснятым задним числом суткам —
  `null`. Записать туда `false` = обвинить клуб в НАШЕМ простое. Разведено на всём пути до экрана.
  Следствие: запрос heartbeat по `Devices` намеренно НЕ ограничен окном времени — фильтр по времени
  выкинул бы филиал из словаря и схлопнул `false` в `null`. Запрос агрегирующий (строка на филиал).
- **Сутки — в часовом поясе филиала** (`BranchEntity.PreferredTimeZone`, у поля это в комментарии и
  записано), не в UTC: клубы UTC+5 работают ночью. Правило живёт в одном `BranchLocalTime`, общем
  для свёртки и для окна отчёта. Раннер берёт UTC-окно с запасом в сутки по обе стороны.
- Свёртка — чистая функция `BranchDailySnapshotBuilder` (17 тестов), раннер только достаёт и пишет;
  фиксированное число запросов на всё окно. Досъёмка ≤30 дней и НЕ раньше `CreatedAtUtc` филиала.
- Экран — вкладка «Динамика» в паспорте организации (право `platform.organizations.view`, как у
  «Клубов»), селектор клуба, сноска о суточной точности. `MissingDayCount` не считает сутки до
  рождения филиала.
- Попутно: правило выручки филиала вынесено из `EfOperatorDashboardService` в общую `BranchRevenue`
  (POS-нетто `payment`/`refund` + `GameplayCharge` + `PostpaidDebt` − `Refund`). Тесты дашборда
  прошли без правок ожиданий — поведение не поехало.

## Продуктовые решения

- **SMS-получатели — в конфигурации (`Alerts:SmsRecipients`), не в БД.** У `PlatformAdminUserEntity`
  телефона нет вообще. Заводить поле + экран + подтверждение номера ради аварийного канала для
  команды из единиц человек = переоткрывать волну A. Цена: смена дежурного номера требует деплоя.
- **Критические письма идут мимо очереди уведомлений** — одна из аварий, о которой кричим, это
  смерть очереди, и письмо через неё не уйдёт никогда.
- **Отбоя по SMS нет.** Разбудить ради «снова всё хорошо» — способ научить игнорировать следующую SMS.
- Внешний мониторинг (Prometheus/Sentry), Telegram-бот, настройки подписки на алерты и непрерывное
  измерение доступности агентов — сознательно НЕ делаются (обоснования в спеке).

## Durable-уроки (все четыре Critical были дефектами ПЛАНА, не исполнителей)

Общая природа: план описывал happy path и не додумывал отказной сценарий. Тесты бы их не поймали —
в плане не было ни одного теста на путь ошибки. Ловило ревью.

- **Самодельный предикат `catch ... when` ловит не то.** `Entry(x).State == Added` истинно после
  ЛЮБОГО неудачного `SaveChangesAsync` → посторонняя ошибка БД проглатывается под видом гонки.
  В проекте есть `RelationalFailureClassifier.IsUniqueViolation(exception, constraintName)` — он
  сверяет `SqlState` и имя constraint'а по цепочке InnerException. Образцы: `InvoiceNumbering`,
  `PlatformAdminDirectoryService`.
- **Резервный канал не должен зависеть от основного.** Почта и SMS в одном `try` = сбой почты
  отменяет аварийную SMS ровно в её сценарии. Разводить на независимые пути, отказ одному
  получателю не отменяет остальных.
- **Обслуживание не решает, успешна ли работа.** Чистка старых записей в общем `catch` тика
  превращала свой случайный сбой в «задание провалилось» → через 3 тика инцидент о самом стороже.
- **Холодный старт.** «Нет ни одного прогона» ≠ «просрочено немедленно»: на первом деплое таблица
  прогонов пуста у всех, и сторож разослал бы SMS «счета не выставляются» про исправную систему.
  Окно отсчитывается от старта процесса (constructor-time capture в singleton hosted service);
  по его истечении молчание задания обязано поднимать тревогу.
- **Тест гонки зелен и на сломанном catch**: в его сценарии единственная возможная ошибка — та
  самая. Нужен отдельный тест, что посторонний `DbUpdateException` **пробрасывается**.
- **`ResolveMissing`-семантика**: закрывать только инциденты видов, которые этот проход реально
  проверял, иначе вызывающий молча закроет чужие. Инвариант выражать сигнатурой, не соглашением.

## Durable-уроки плана 2 (снова дефекты ПЛАНА, но ловились раньше)

Закономерность: я писал код в плане и не сверял его с собственными же тестами из того же плана.
В отличие от плана 1, здесь три из четырёх поймали исполнитель и потасочное ревью, а не финальное.

- **Референсный код в плане может противоречить тесту в том же плане.** Бэкфилл по фиксированному
  окну давал новой организации 31 строку, а тест этажом выше требовал одну. Исполнитель остановился
  и починил, а не подогнал тест.
- **Не называть все виды сущности — значит проверить не то.** `InvoiceKindNames.Credit` не был назван
  в плане; тест кредит-ноты использовал `OneOff` и проходил бы даже при поломке реального пути.
- **Своё деление на 100 рядом с `minorToMajor`** — тот же класс, что тиражирование обходняка возле
  работающей инфраструктуры. Сейчас совпадает случайно, разойдётся молча.
- **ICU-plural-ключ, вызванный без `count`, отдаёт СЫРОЙ шаблон** (`catch` в `createTranslator`
  возвращает неформатированное сообщение). Использовать plural-ключ как статичную подпись нельзя —
  нужен отдельный ключ. Поймало только финальное ревью: тесты рендера этого не проверяли.
- **Граница окна отчёта.** `SubscriptionMovement` требует буфер снимков за месяц ДО начала окна,
  иначе все платившие ранее попадут в «пришли» первого месяца. Контракт закреплён в XML-doc и тестом.
  Отдельно: при первом включении фичи истории нет вовсе, всплеск структурно неизбежен — на экране
  стоит сноска, потому что молча показать взлёт как рост = то же враньё, что «Долгов нет» в волне B.

## Durable-уроки плана 3 (снова дефекты ПЛАНА; ловились и рано, и поздно)

- **Одно и то же правило в двух местах — вопрос времени, а не вероятности.** «Сколько филиал
  заработал» жило только в дашборде; второй экземпляр в снимках разошёлся бы молча. Тот же класс,
  что деление на 100 рядом с `minorToMajor` в плане 2. Проверять перед новой фичей: не считаю ли я
  заново то, что проект уже считает.
- **Часовой пояс надо держать на ВСЁМ пути, а не в одном конце.** Свёртка писала местные даты, а
  окно отчёта я в плане посчитал по UTC — в Душанбе после 19:00 UTC самый свежий день выпадал из
  ответа. Поймало ревью задачи; фикс = общий `BranchLocalTime` для обоих концов.
- **«Нет данных» — не только про поле, но и про счётчики над ним.** `MissingDayCount = окно −
  снимки` объявлял пробелом наблюдения сутки до создания клуба: трёхдневный клуб получал «27 дней
  без наблюдения». Тот же подлог уровнем выше `AgentAlive`; поймало только ФИНАЛЬНОЕ ревью ветки.
- **Тест идемпотентности на InMemory ничего не доказывает про уникальный индекс** — InMemory их не
  знает. Такой тест надо честно переименовать в то, что он проверяет, и рядом завести настоящий
  Postgres-тест гонки (`SaveOverlapGate`, образец `PlatformIncidentConcurrencyPostgresTests`).
- Ревьюер задачи нашёл «запрос heartbeat не ограничен окном» — правильный ответ был НЕ чинить:
  наивный фильтр схлопнул бы `false` в `null`. Находка ревью не обязана иметь предложенное решение.

## Открытое

- **Смешанные валюты в MRR**: суммируется без группировки, `CurrencyCode` берётся из первой подписки.
  Унаследовано от `EfBillingMetricsService`, не привнесено волной C. В проекте есть строгий образец —
  `LedgerBalanceProjector` (`SingleOrDefault` по валюте). Риск низкий: планы засеяны только в TJS.
- **Текущий MRR на экране аналитики не учитывает скидку**, тогда как суточный снимок учитывает —
  тот же унаследованный изъян `EfBillingMetricsService`.

- Отложенные миноры (финальным ревью признаны не блокирующими): мёртвый белый список в
  `PeriodicJobRegistrationTests`; ротация `platform_job_runs` не покрыта тестом (InMemory не знает
  `ExecuteDeleteAsync`); шесть счётчиков очередей идут последовательно вместо `Task.WhenAll`;
  `lastError` на экране — сырое сообщение исключения.
- `MissingDayCount` не защищён `Math.Max(0, …)`: уйдёт в минус, если снимки нарушат инвариант
  «не раньше рождения филиала». Сейчас невозможно, свойство предсуществующее.
- tg-переводы экранов не носитель-ревьюированы; по плану 3 сомнительны «Тағйирот» как перевод
  «Динамика» и длинная сноска о суточной точности. Ранее по плану 1: `auto_protection`
  «Ҳифзи худкори сеанс», `health_watch` «Назорати саломатӣ», единый корень «ирсол» для
  `notification_*`. Слово «биллинг» стоит явно внести в список заимствований в шапке guard-теста
  `packages/i18n/src/messages.test.ts` — оно уже дважды использовано как прецедент.
