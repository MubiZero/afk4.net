**Видение (озвучено пользователем 2026-07-20):** operator-app = единая веб-админка клуба внутри
тонкой обёртки; функционал раздаётся **по роли пользователя** (owner сети/доверенный админ vs
админ ПК-клуба vs кассир vs техник). Один web-app → можно совать в разные хосты: сейчас WPF
(десктоп), потенциально мобильная обёртка → админить с ПК И с мобилы.

**Независимые куски (декомпозиция):**
1. **Ролевая модель/доступ** — УЖЕ есть: `permissionNames` (`src/AFK4.OrganizationAdmin.Web/src/permissionNames.ts`)
   + серверные роли. Строить не нужно; нужно решать «какая роль что видит». Owner/доверенный-админ
   гейт для настроек филиала = `manageBranchSettings` (`branches.settings.manage`).
2. **Консолидация owner-панели → оператор — СДЕЛАНА** (проверено по коду 2026-08-10). Отдельного
   owner-фронта в репозитории нет; его функции живут в Операторе разделом **«Сеть»**
   (`src/AFK4.OrganizationAdmin.Web/src/network/`, каркас `279a1a08`): Филиалы = свод по сети с
   today-KPI (гейт `branches.view`, «открыть филиал» намеренно не делали — переключение живёт в
   `useActiveBranch`), Подписка = read-only зеркало плана/статуса/счетов (управление тарифом
   остаётся на стороне платформы), Установка устройств, Журнал аудита организации. Сотрудники и
   роли уровня сети — `management/destinations/StaffRolesDestination.tsx` (5 операций портированы
   1:1 из `SettingsStaffSection`, двойной permission-гейт). Каждое направление видно по правам
   (`networkNav.ts::allowedNetworkDestinations`).
3. **Мобильная обёртка** — тот же web-app в мобильном хосте (аналог WPF-хоста
   [[afk4-operator-app-webview2]]). Инфра-эпик: хост, адаптив, тач-таргеты ≥44px.

- Требование одобрять устройства (device-approval) — ОТКАЗАЛИСЬ. Не тащить в новые экраны.
