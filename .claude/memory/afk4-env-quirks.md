- **i18n locale JSON lives at repo-root `locales/{ru,en,tg}.json`** (NOT `packages/i18n/locales/`). After editing, regenerate the typed `packages/i18n/src/messages.ts` with `cd packages/i18n && "$BUN" run gen`. `t()` is strictly typed by `MessageKey`, so a new `op.*` key won't typecheck until added to all three locales AND regenerated. Operator-web nav: `workspaceIds` (operatorPermissions.ts) and `navItems` (operatorData.ts) are **index-parallel** — App.tsx maps `workspaceIds[index]` to each navItem; keep both arrays the same length/order when adding a workspace. New workspace also needs: WorkspaceId union (operatorTypes.ts), workspacePermissionRules entry, App.tsx render block, and a SummarySidePanel exclusion if full-screen.
- **bun** is installed at `/home/fedya/.bun/bin/bun` (v1.3.14) but is **NOT on the shell PATH** in the Bash tool. Call it by full path (e.g. `BUN=/home/fedya/.bun/bin/bun; "$BUN" test`). Verify before assuming it moved to PATH.
- The repo's web apps run **`bun test`** (not vitest runner) and **`bun run build`** (= `tsc -b && vite build`). Run both — esbuild/bun skip type-checks, so green tests can still have type errors.
- **New `src/styles/NN-*.css` file → RESTART `bun run dev`.** styles.css is a postcss `@import` barrel; a long-running dev server does NOT pick up a newly-created imported CSS file — it 500s `[postcss] ENOENT … ./styles/NN-*.css` and serves a BLANK white page, even though `bun run build` (fresh process) is green. Symptom: console `styles.css → 500 Internal Server Error`. Fix: kill+restart the dev server. (Editing an existing CSS file HMRs fine; only a brand-new imported file needs the restart.)
- **rtk (Rust Token Killer) proxies shell output and strips code comments** from `cat`/file dumps to save tokens. This made `cat money.ts` show a function body WITHOUT its inline comment that the Read tool showed. **Trust the Read tool for exact file content, not `cat`.**
- **rtk also mangles some commands/output**: it broke `sudo docker run … pg_dump …` with `sudo: rtk: command not found` (triggers on the `pg_dump` token), and it reformats piped `curl … | python3`/JSON output into a *schema* (`{status: string}`) instead of real values. **Workaround: put the command in a `/tmp/x.sh` script and run `bash /tmp/x.sh`** — rtk only sees `bash file` and leaves it alone. Save curl JSON to a file then parse the file.
- **`dotnet ef` on Linux works** (SDK 10.0.300, ef tool 10.0.4) for `migrations add`. TWO traps: (1) `--no-build` reuses the LAST build of the API project — if you edited an entity/DbContext since then, the model is STALE and you get an EMPTY migration (blank Up/Down). Fix: `dotnet build src/AFK4.Platform.Api` FIRST, then `migrations add ... --no-build`. (2) `dotnet ef migrations remove` connects to the DB (127.0.0.1:5432) to read applied history and FAILS if no local PG is up — to undo an unapplied/empty migration just `rm` both the `.cs` + `.Designer.cs` (and check `git status` that ModelSnapshot wasn't touched). Migration output dir: `src/AFK4.Platform.Api/Data/Migrations`.
- **docker** IS available in WSL (v29.x, needs `sudo`). Useful for version-matched DB tooling: server is `postgres:17`, but Fedora's client is pg16 (pg_dump16 refuses a v17 dump) → run `sudo docker run --rm -v /tmp:/out postgres:17-alpine pg_dump/psql …`.

- `cd` persists between Bash calls (same shell cwd) and a later relative `cd` can fail; prefer absolute paths.
- **Windows exes on PATH (bridge for `powershell.exe` etc.):** `~/.zshenv` appends `/mnt/c/Windows/System32{,/WindowsPowerShell/v1.0}` + `/mnt/c/Windows` (done 2026-06-02). New tool sessions / `zsh -c` subshells inherit it; the *current* persistent tool shell snapshots PATH at session start so it WON'T pick up a mid-session `~/.zshenv` edit — export inline for that call. `appendWindowsPath=false` is why it's needed.
- **`AFK4.Agent.Service.Tests` baseline on WSL = 26 pre-existing failures** in `ClientReleaseAutomationTests` (25) + `ExternalProcessAgentRestartSchedulerTests` (3) — they need real Windows release tooling (powershell/signtool/minio/process-restart) and fail with `powershell.exe ... No such file or directory` even with the PATH bridge (vstest host doesn't inherit it). NOT a regression; ~141 pass. Filter them out when checking your own agent tests.
- **Agent worker test gotcha (`AgentUpdateWorker`/`Worker` fail-fast on unconfigured):** both `BackgroundService` workers early-`return` from `ExecuteAsync` when `AgentOptions.IsConfigured` is false. `IsConfigured` requires `OrganizationId`+`BranchId`+`DeviceId` ≠ `Guid.Empty` AND `PlatformBaseUrl` https + non-loopback. A test that builds `AgentOptions { UpdateCheckIntervalSeconds = ... }` without those gets a worker that never calls its coordinator → `TaskCompletionSource.WaitAsync(60s)` **times out** (looks like flaky timeout, is deterministic). Always set the configured fields (mirror `WorkerTests`). Fixed in `AgentUpdateWorkerTests` 2026-06-11.

## Windows bridge (for WPF — net10.0-windows builds/tests)

WSL distro is `FedoraLinux-42`. WPF projects (`AFK4.OrganizationAdmin.App`, `AFK4.Player.Shell`) only build on Windows. Bridge via WSL→Windows interop:

1. **Interop binfmt is missing on boot** (despite `/etc/wsl.conf` `[interop] enabled=true`) — `cmd.exe` gives `exec format error`. Re-register it (passwordless sudo IS available):
   `echo ':WSLInterop:M::MZ::/init:PF' | sudo tee /proc/sys/fs/binfmt_misc/register`
   Ephemeral per WSL boot; a `wsl --shutdown` + restart (run by the user from Windows) makes the wsl.conf setting stick permanently. `appendWindowsPath=false`, so call Windows exes by full path.
2. **Windows .NET**: `/mnt/c/Program Files/dotnet/dotnet.exe` (SDK 10.0.203; WindowsDesktop ref 10.0.7 present → WPF builds). Verified: built `AFK4.Player.Shell` with 0 errors.
3. **Pass Windows UNC paths** to `dotnet.exe` (it does NOT understand `/home/...`). Repo = `\\wsl.localhost\FedoraLinux-42\home\fedya\projects\afk4.net`. Example: `"/mnt/c/Program Files/dotnet/dotnet.exe" build '\\wsl.localhost\FedoraLinux-42\home\fedya\projects\afk4.net\src\AFK4.Player.Shell\AFK4.Player.Shell.csproj'`.
4. **Cross-OS obj/bin collision**: Linux `dotnet` and Windows `dotnet.exe` share the same `obj/bin` and stomp each other → CS0006 "metadata file ref/...dll not found" cascades. Before a Windows build (or switching back to Linux), clean: `find src -type d \( -name obj -o -name bin \) -prune -exec rm -rf {} +`. Use `dangerouslyDisableSandbox: true` on the Bash call when invoking Windows exes.
6. **Sync an UNPUSHED WSL branch into the D: clone without GitHub (verified 2026-06-09):** local-path fetch works — `cd /mnt/d/projects/afk4.net && git fetch /home/fedya/projects/afk4.net <branch>:<branch>` (or `git fetch … <branch>` then `git merge --ff-only FETCH_HEAD`), then run Windows tests: `powershell.exe -NoProfile -Command "cd D:\projects\afk4.net; & 'C:\Program Files\dotnet\dotnet.exe' test tests\<Proj>\<Proj>.csproj --nologo"` (native `D:\` path → vstest runs; test summary line is in Russian: `Пройден! : … пройдено N`). WSL `git -C /mnt/d/...` fetch/checkout is fine (objects only); CRLF only distorts working-tree *status*. For the host build to copy web assets, build the web `dist` in WSL and `cp -r` it into the D: clone's `src/AFK4.Player.Shell.Web/dist` first (bun is WSL-only).
5. **Dedicated native Windows clone for WPF (RECOMMENDED, set up 2026-06-03) — supersedes the UNC approach in #3 for test runs:** `D:\projects\afk4.net` (= `/mnt/d/projects/afk4.net`) is a clean clone authed via Windows `gh.exe` (account MubiZero, keyring; `gh.exe` at `/mnt/c/Program Files/GitHub CLI/gh.exe`). Build/run WPF there: `"/mnt/c/Program Files/dotnet/dotnet.exe" test "D:\projects\afk4.net\tests\<Proj>\<Proj>.csproj"`. A native NTFS path avoids BOTH the UNC issue AND the cross-OS obj/bin collision (#3/#4), and — unlike `\\wsl.localhost` paths — **vstest can actually RUN tests** (over UNC it dies with "test source .dll not found", build-only works). Verified there on sp4-localization: Player.Shell.Tests 12, Operator.App.Tests 235, Localization.Tests 15, all pass. Git ops via `"/mnt/c/Program Files/Git/cmd/git.exe" -C "D:\projects\afk4.net" …`. **CRLF caveat:** this clone has `core.autocrlf=true`, so inspecting it with WSL `git` shows EVERY file as phantom-modified (LF↔CRLF) — use Windows `git.exe` for an accurate status. To delete/move it from WSL use WSL `rm`/`mv` on `/mnt/d/...`; `cmd.exe` launched from a `\\wsl$` cwd refuses ("UNC paths not supported as current directory").
