## Operator UI in a plain browser vs staging (no native host needed)
Operator auth is normally obtained via the native WebView2 host bridge (`postHostRequest('auth:signIn')`), which rejects in a plain browser — BUT the access token lives in JS (`operatorHelpers.ts` `getAccessToken: () => session.accessToken`), so a dev stub that supplies an `OperatorAuthSession` is enough. Harness (WORKING-TREE ONLY in `src/AFK4.Operator.App.Web`, do NOT commit):
- `vite.config.ts`: `server.proxy` for `/api` and `/hubs` (ws) → `https://afk4.staging.mubi.dev` (changeOrigin) — avoids CORS; browser stays same-origin.
- `index.html`: inline classic `<script>` that sets `window.__AFK4_OPERATOR_CONFIG__` (`platformBaseUrl: location.origin+'/'`, currencyCode TJS, org/branch ids) and installs a `window.chrome.webview` stub implementing the host message protocol (`{type,requestId,payload}` → `{type:'host:response',requestId,ok,payload}`) for `auth:signIn` (POST `/api/auth/staff/sign-in`, body `{organizationId,userName,password}` → maps `StaffSignInResponse`→`OperatorAuthSession` 1:1; refreshToken kept in a closure), `auth:loadToken`(→null so login shows), `auth:refresh`, `auth:signOut`; `window:*` commands no-op.
- Run from WSL: `cd src/AFK4.Operator.App.Web && /home/fedya/.bun/bin/bun run dev` → `http://127.0.0.1:5174/` (WSL2 forwards localhost to the Windows host browser). Login `e2eowner` / `E2eOwner!2026`. Verified: sign-in through the proxy returns 200.

## Operator NATIVE WPF (WebView2 host) vs staging — preferred over the browser stub (verified 2026-06-11)
The native `AFK4.Operator.App` reads its backend config from **env vars** (`OperatorAppOptions.cs`): `AFK4_OPERATOR_PLATFORM_BASE_URL` (default localhost:5074), `AFK4_OPERATOR_ORGANIZATION_ID`, `AFK4_OPERATOR_BRANCH_ID`, `AFK4_OPERATOR_CURRENCY_CODE` (default TJS). The host injects these into the WebView via `OperatorWebBootstrapScript` → `window.__AFK4_OPERATOR_CONFIG__`; the React UI is served from a virtual host `https://operator.afk4.local` (CORS-whitelisted on the API). Launcher: `D:\projects\afk4.net\run-operator.ps1` (sets the 4 env vars to staging + `& $exe` the self-contained publish `artifacts\client-packages\publish\operator-app-<ver>-internal\AFK4.Operator.App.exe`). Real host-bridge auth → log in `e2eowner`/`E2eOwner!2026`. Needs WebView2 Runtime (dev box has it). **THREE gotchas that all bit on 2026-06-11, fixed:**
1. **Stale persisted USER env on the box** — a prior session left `AFK4_OPERATOR_PLATFORM_BASE_URL=http://localhost:5074/` + a foreign org/branch (`0c04d6c0…`/`acfc0212…`) at the Windows **User** scope. Overwrote them to staging values with `[Environment]::SetEnvironmentVariable(name,val,'User')`.
2. **`Start-Process` does NOT propagate in-process `$env:` overrides** (UseShellExecute uses the original user env block). Launch the exe with the call operator `& $exe` instead so it inherits the modified environment.
3. **THE BIG ONE — the dev browser-harness baked into the built dist.** The dev-only host-bridge stub lives in `src/AFK4.Operator.App.Web/index.html` (committed as the "DO NOT MERGE" harness). When operator web is built for packaging, that inline `<script>` ships in `dist/index.html`; inside the native host it **clobbered the real `window.chrome.webview` bridge and overwrote `__AFK4_OPERATOR_CONFIG__.platformBaseUrl` to `location.origin` (operator.afk4.local)** → every fetch hit the WebView origin → "Failed to fetch" + offline/degraded demo data. **Fix (uncommitted, in WSL repo + D: clone):** guard the stub IIFE with `if (window.chrome && window.chrome.webview) { return; }` so it stays inert in the native host and only activates in a plain browser. Must rebuild operator web dist after editing index.html.
Also: stale **token + floor-map cache** live at `%LOCALAPPDATA%\AFK4\Operator\` (`tokens.bin`, `cache\floor-map-cache-<branchId>.json`). Auto-loaded token persists across orgs and degraded UI shows the cached floor map of the OLD branch → looks like demo data. To start clean: kill the exe, delete `tokens.bin` + `cache\`, relaunch → fresh login. Verified end state: correct platform shows in the SignInScreen "ПЛАТФОРМА" panel, login works, real staging seats render.

## VM walkthrough (user-driven; backend = staging by default)
1. Copy `afk4-agent-…msi` + `afk4-player-shell-…msi` into the VM (VMware shared folder / drag-drop).
2. Install the **agent** MSI (admin; SmartScreen→Run anyway). It installs Agent.Service + SetupWizard and launches the wizard.
3. Wizard → sign in as staff `e2eowner`/`E2eOwner!2026` → pick the club/branch → role **gaming_pc** → create a seat (none exist) → enroll. Wizard configures + starts Agent.Service.
4. Install the **player-shell** MSI (the gaming_pc Agent supervises Player.Shell; channel pull may be empty, so install directly).
5. In the operator browser, refresh → the new seat appears → start a session on it → the VM Agent gets the lease → Player.Shell shows the active session/timer.

## End-to-end smoke 2026-06-11 — client bugs found & fixed (all SHIPPED to main)
Driving the full operator→agent→shell→session loop surfaced four real client bugs, fixed in code:
1. **build-client-packages.ps1:236** — `Remove-Item -LiteralPath …\*` (literal `*`) broke packaging; → `Get-ChildItem | Remove-Item`.
2. **Operator dev-harness baked into dist** (index.html) clobbered the native WebView2 bridge → guarded with `if (window.chrome && window.chrome.webview) return;` (see the Operator NATIVE WPF section above).
3. **Player.Shell WebView2 user-data folder** defaulted next to the exe in read-only Program Files → `EnsureCoreWebView2Async` threw in async-void `OnLoaded` → kiosk crash-loop (agent relaunches every ~30s; agent.log shows "Player Shell process start requested" repeating). Fix: `PlayerWebView2UserDataFolder` → `%LOCALAPPDATA%\AFK4\Player\WebView2` + `CoreWebView2Environment.CreateAsync(userDataFolder:)`, mirroring operator; plus a try/catch in OnLoaded + App.OnStartup writing to `%ProgramData%\AFK4\logs\player-shell.log` (`PlayerShellStartupLog`) so future shell crashes aren't mute.
4. **THE unlock bug — `SetupWizardWebHostBridge.cs`** hardcoded `LeaseSigningPublicKeyPem: string.Empty` (AND UpdatePackageSigningPublicKeyPem) at BOTH enroll paths (owner-code ~196 + staff `EnrollAuthenticatedAsync` ~407) when writing bootstrap.json. The legacy WPF `SetupWizardViewModel.cs:307` did it right. Result: agent's bootstrap had an empty lease public key → `SessionLeaseValidator` → unlock "Rejected: Lease signing public key is not configured." Fix: use `response.LeaseSigningPublicKeyPem` / `response.UpdatePackageSigningPublicKeyPem`. NOTE: staging IS correctly configured — `Sessions__SigningPrivateKeyPem` is set (the platform derives the public key in the enroll response via `EfInstallService.ResolveLeaseSigningPublicKeyPem`); the bug was purely client-side dropping it. Lease sig = ECDSA-P256-SHA256.

### Operator "Офлайн" banner bug (2026-06-11, fixed) — staleness clock not reset by realtime
Symptom: operator floor map intermittently showed a top banner "Офлайн: ждём подтверждение платформы" (and the seat looked offline) even though the platform was fully correct (verified: WB-13 isOnline=true, isLocked=false, pendingCommandCount=0, floor-map state=Active; and a direct @microsoft/signalr client against staging /hubs/devices with the e2eowner token received deviceStatusChanged events every ~10s with online=true — so the hub + groups + DTOs are all fine). Root cause was CLIENT-side and NOT the seat tiles (those rendered correctly via realtime): the banner is the data-staleness indicator. `offlineBannerText` (floorMapState.ts, staleAfterMs=30_000) shows it when `cachedAtMs` is older than 30s, and `cachedAtMs` was only advanced on a full HTTP floor-map reload (mapFloorMapDtoToState). The realtime `onDeviceStatusChanged` handler (useOperatorRealtime.ts) updated `seats` but spread `...current` keeping the old `cachedAtMs`, so 30s after the last HTTP reload a LIVE, realtime-fed map was flagged stale. A manual page reload reset cachedAtMs (hence "reload fixes it for ~30s"). Fix: realtime device-status apply now sets `cachedAtMs: Date.now()`. (Note for any future digging here: the floor-map online uses `IsHeartbeatFresh` = device.IsOnline && lastHeartbeat within `BranchDiagnosticsOptions.StaleHeartbeatSeconds`=300s, whereas the /devices list returns the sticky DB IsOnline flag — that's why /devices showed WB-11 online 15min after its last heartbeat. Heartbeat cadence is 10s. SessionLeaseValidator/unlock path is fine once the wizard delivers the lease key.) Secondary latent bug left as-is: feedbackText() ignores `detail` for state==='pending', so MapWorkspace's offline FeedbackNotice (state:'pending', detail:offlineBanner) would show the generic "ждём подтверждение платформы" instead of the "Офлайн — данные от HH:MM" detail if it ever genuinely goes stale — cosmetic, low priority.
