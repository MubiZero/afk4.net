# Домены и адреса AFK4

Status: схема принята частично — заведено то, что работает сегодня. Последнее обновление
2026-09-03.

## Правило, из которого всё следует

**Запись в DNS заводится вместе с приложением, которое на этот адрес отвечает, а не заранее.**
Имя, указывающее на сервер, где для него нет маршрута в Traefik, не «ждёт своего часа»: оно
отдаёт чужую заглушку, сертификат Let's Encrypt на него не выпускается, и посетитель видит
ошибку TLS. Пустая зона честнее полузаполненной.

## Что есть сейчас

В зоне `afk4.net` заведено только почтовое и защита сертификатов:

| Тип | Имя | Значение | Зачем |
|---|---|---|---|
| MX | `afk4.net` | `mail.mubi.dev` (10) | почта, см. `email-delivery.md` |
| TXT | `afk4.net` | `v=spf1 mx -all` | |
| TXT | `_dmarc.afk4.net` | `v=DMARC1; p=none; …` | |
| TXT | `_smtp._tls.afk4.net` | `v=TLSRPTv1; …` | |
| CAA | `afk4.net` | `0 issue "letsencrypt.org"`, `0 iodef "mailto:postmaster@mubi.dev"` | сертификат для домена вправе выпускать только Let's Encrypt |

К записи CAA Cloudflare автоматически дописывает свои удостоверяющие центры (`digicert.com`,
`pki.goog`, `ssl.com`, `comodoca.com`) — они нужны для его собственных краевых сертификатов,
это штатное поведение, а не чужое вмешательство.

Учётная запись ACME в CAA намеренно не указана. Сертификаты выпускают двое — Traefik в
Coolify для приложений и Stalwart для почты, — у каждого своя учётная запись, и пиннинг
одной сломал бы вторую. У `mubi.dev` пиннинг есть, потому что там выпускает только Stalwart.

**Production приложений AFK4 не существует.** В Coolify живут два приложения, оба staging и
оба на личном домене: `afk4.staging.mubi.dev` (Platform API) и
`platform.afk4.staging.mubi.dev` (Platform Control), плюс сервис MinIO с пакетами обновлений.

## Куда это идёт

| Имя | Что отвечает | Когда заводить |
|---|---|---|
| `afk4.net`, `www.afk4.net` | лендинг платформы | когда появится сам лендинг |
| `api.afk4.net` | Platform API | вместе с production-приложением |
| `platform.afk4.net` | Platform Control (внутренняя панель) | вместе с ним же |
| `updates.afk4.net` | хранилище пакетов обновлений (MinIO) | вместе с production-хранилищем |
| `status.afk4.net` | страница доступности | когда будет что показывать; сейчас монитор пишет в Telegram |
| `mail.mubi.dev` | почта — **остаётся где есть** | не переносим |

Почтовый хост осознанно не переезжает на `afk4.net`: обратная зона IP указывает на
`mail.mubi.dev`, и на этом имени наработана репутация отправителя. Домен в адресе письма
(`no-reply@afk4.net`) от имени сервера не зависит.

**Поддоменов на клуб не будет.** Раньше клуб определялся по адресу (`клуб.afk4.net`); в
приложении игрока от этого отказались — клуб выбирается внутри приложения из каталога
(`2026-08-11-customer-app-flutter-design.md`). Значит ни wildcard-записи, ни wildcard-серти­фиката
не требуется.

## Что тронет переезд staging на afk4.net

Отдельная задача, и не однострочная: адрес staging зашит в местах, где смена хоста ломает уже
работающее.

- `Cors__PlatformWebOrigins__0` и `VITE_PLATFORM_API_BASE_URL` — иначе панель не достучится
  до API;
- `DcGate__WebhookUrl` — вебхук платежей прописан в проектах dcgate на стороне шлюза;
- базовый адрес хранилища обновлений: адреса артефактов уже зарегистрированы в пакетах и
  неизменяемы по замыслу;
- `Install__ApiBaseUrl` — **этот адрес записывается в машинную конфигурацию агента при
  установке**. Уже зарегистрированные ПК продолжат ходить на старый адрес, пока их не
  переустановят или не обновят конфигурацию;
- монитор доступности в Cloudflare Workers и рунбуки, где адрес указан дословно.

Пока первого клуба нет, переезд ничего не даёт; после — потребует плана вывода.

## Прокси Cloudflare

Почтовые записи — всегда без прокси (серое облако). Для будущего `api.afk4.net` включение
прокси нужно решать отдельно: через него идут постоянные соединения SignalR (карта зала,
команды устройствам), и краевой прокси добавляет свои таймауты и разрывы. Staging сегодня
работает напрямую, и это самый предсказуемый вариант для первого клуба.
