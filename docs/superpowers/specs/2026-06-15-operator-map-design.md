# Operator App — Этап 1 «Карта»

**Дата:** 2026-06-15
**Статус:** дизайн на ревью
**Охват:** `AFK4.Operator.App.Web` (фронт) + `AFK4.Platform.Api` (пространственная модель пола — кусок B1)

## Контекст

Этап 0 «Фундамент» полностью закрыт (PR #87/#88). Это первый **областной** этап: «Карта» —
зал целиком, главный экран оператора после входа. Цель — превратить Карту из «таблицы статусов»
в **командный центр смены**: зал считывается глазами за полсекунды, операции под рукой, ничего
критичного не теряется из виду; плюс возможность **расставить план зала** мышью.

Опираемся на готовый фундамент Этапа 0: командный реестр (`operatorCommands.ts`,
`createCommandRegistry` → пустой обработчик даёт честный toast `op.command.deferred`), палитра/«+»,
хоткеи (`useHotkeys`), `ShellAlerts` (строка тревог со швом `sources`), примитивы Toast/Skeleton/
EmptyState, единый формат денег (`formatMinorUnits`, `currencySymbol`), токены `@afk4/tokens`,
i18n `@afk4/i18n` (ru/en/tg).

**Стартовая точка (код):** `MapWorkspace.tsx` (плитки + таблица + тулбар «Управление ПК»),
`MapSidePanel.tsx` (правая панель сессии, ~720 строк), `floorMapState.ts` (маппинг DTO→состояние,
тон/статус/остаток). Бэкенд: `FloorMapEndpoints.cs`, `SeatStatusDto`/`FloorMapDto`, `SeatEntity`/
`ZoneEntity`, `EfFloorMapReadService`/`EfFloorMapEditService`.

**Бэкенд-реальность (проверено):** место несёт только `SortOrder`, зона — отдельная сущность с
`SortOrder`. **Пространственной модели нет** (координат/типа/поворота/геометрии зон/стен).
Сервис редактирования пола уже существует (`EfFloorMapEditService` + `FloorMapBulkUpdateRequest`) —
кусок B1 его **расширяет**, не пишет с нуля.

## Объём и декомпозиция

Полный Этап 1 = **командный центр (A)** + **редактор плана зала (B)**. По образцу Этапа 0
(одно направление = свой `план → PR`) режем на 5 кусков. Порядок: A1 → A2 → A3 → B1 → B2
(сначала дешёвая ежедневная ценность на чистом фронте, потом бэкенд-тяжёлый редактор).

| Кусок | Что | Слой |
|---|---|---|
| **A1** | Язык плиток: канон статусов, предоплата/постоплата, свободно=«＋» | фронт |
| **A2** | ПКМ контекст-меню + строка критсостояний со счётчиками | фронт |
| **A3** | Полировка правой панели (конкретика, доступ к операциям) | фронт |
| **B1** | Пространственная модель пола (координаты/тип/поворот/зоны-геометрия/стены) | бэкенд |
| **B2** | Вид «План» + редактор расстановки; «Сетка» рисует по координатам | фронт (+B1) |

**Виды Карты:** **Сетка · Таблица** остаются двумя рабочими видами для сканирования. **«План»** —
отдельный **режим-редактор** (инструмент расстановки, не третий «вид» для сканирования). Исходная
фиксация Этапа 0 «Сетка·План (без Оба)» уточнена: Таблица — это список-данные, не отрисовка пола,
её сохраняем; «План» приходит как редактор в B2.

## 1. Язык плиток (кусок A1)

Канон визуального языка места (залочен в Этапе 0 §«Визуальный язык места», здесь доводится в коде):

- **Статус = спокойная база + полоса слева; громкий цвет только Внимание/Проблема.** Тон места —
  существующие 7 значений `SeatTone` (`ready/active/pending/warning/blocking/offline/service`).
  Класс `state-${tone}` уже есть в `styles.css` — доводим так, чтобы спокойные тоны
  (`ready/active`) были сдержанными, а «громкими» оставались только `warning/blocking/offline/
  service`. Статус читается **не только цветом** (полоса + чип-подпись + иконка).
- **Один размер плитки, density НЕТ.** Выбранное место подсвечивается без изменения размеров сетки.
- **Предоплата** (фикс-сессия с остатком): остаток времени внизу + полоса прогресса убывания.
- **Постоплата / открытый счёт** (нет обратного отсчёта, набегает сумма): сумма наверху со стрелкой
  роста, «54 с. ▲» (формат через `formatMinorUnits` + `currencySymbol`; TJS → «с.»). Источник —
  `accruedCostMinorUnits` (уже маппится в `floorMapState.ts`, поле `isOpenTab`).
- **Свободное место** зовёт действием: крупный **«＋»** вместо пустоты (приглашение посадить).
- **Большой зал = скролл** сетки; ничего не сжимаем под экран.

*Чистый фронт: `MapWorkspace.tsx` (`SeatTile`) + `styles.css`. Бэкенд-зависимостей нет —
все данные уже в `SeatSummary`.*

## 2. ПКМ контекст-меню + строка критсостояний (кусок A2)

**Контекст-меню по правому клику на плитке** (и в строке таблицы) — целевая форма операций над
местом/ПК. Раскрытие через существующий командный реестр; диспетчер уже даёт честный
`op.command.deferred` для незарегистрированных. Состав:

- **Живые** (переиспользуют обработчик `onSeatAction` / PC-control, уже подключённый в панели):
  старт сеанса, завершить, +15/+30, пересадка (на свободное место в зале), управление ПК
  (статус/lock/unlock).
- **«Скоро»** (честная заглушка-toast, бэкенда нет): штраф, уведомление игрока, питание сверх lock
  (reboot/shutdown/wake), пересадка между залами. Это помечено отдельными продуктовыми эпиками —
  меню показывает целевую карту возможностей, не вводя в заблуждение (#37).
- Доступность пунктов — по правам (`operatorPermissions`) и по состоянию места (старт только на
  свободном и т.п.), как уже сделано в панели. Клавиатура: меню открывается с клавиатуры, Esc/
  стрелки/Enter; ARIA-роль `menu`.

**Строка критических состояний** — наполнение шва `sources` у `ShellAlerts` (Этап 0): счётчики
«Нет связи · Снят шелл · Обслуживание · Высокий доступ» по тонам/состояниям мест. Клик по счётчику
→ фильтр Карты на эти места. Пожар видно сразу и не пропускаешь.

*Чистый фронт: `MapWorkspace.tsx`, `operatorCommands.ts`, `ShellAlerts`, `styles.css`, i18n-ключи.*

## 3. Полировка правой панели (кусок A3)

Доводим `MapSidePanel.tsx` по принципу «конкретика, которая уже на руках, доезжает до пользователя»
(#34):

- Вместо generic-подписей — **конкретные** данные, которые уже есть в `SeatSummary`/quote: имя
  устройства (`deviceName`), имя/баланс/долг клиента, версии Agent/Shell, точная команда.
- **Точные ошибки** вместо «что-то пошло не так» (используем `projectOperatorFacingError`,
  не оборачивать в generic).
- Доступ к операциям не запрятан: частые действия на виду, статус подтверждения/команды читаем.
- Никаких сырых GUID на нормальном операторском пути (acceptance §`operator-app-ui-target`).

*Чистый фронт, без новых бэкенд-зависимостей.*

## 4. Пространственная модель пола (кусок B1)

Заводим раскладку как **необязательную** надстройку (см. «Принцип на масштаб»): если координат нет —
всё работает как сейчас (поток по `SortOrder`).

**`SeatEntity` (+поля):**
- `PosX: int?`, `PosY: int?` — ячейка сетки (целые, снап «бесплатный»);
- `Rotation: int` (default `0`; 0/90/180/270);
- `SeatType: string` (default `"pc"`; `pc/console/vr/sim/billiard/boardgame/counter`).

**`ZoneEntity` (+поля):**
- `GeoX/GeoY/GeoWidth/GeoHeight: int?` — прямоугольник зоны в ячейках;
- `Color: string?` (токен/hex), `ZoneType: string?` (`reception/wardrobe/wc/lounge/bar/kitchen/hall`).

**`WallEntity` (новая):** `WallId, OrganizationId, BranchId, X1, Y1, X2, Y2, CreatedAtUtc` — отрезок
стены между узлами сетки. Скоуп тенанта — как у Seat/Zone (`OrganizationId + BranchId`).

**Контракты:** `SeatStatusDto` += `PosX, PosY, Rotation, SeatType`; `FloorMapDto` += геометрия зон
+ список стен. `FloorMapBulkUpdateRequest` и `EfFloorMapEditService` расширяются на сохранение
раскладки (позиции мест, геометрия/тип/цвет зон, добавление/удаление стен) одной транзакцией.

**Миграция:** EF Core / PostgreSQL, `src/AFK4.Platform.Api/Data/Migrations/`. Все новые поля
nullable / с дефолтами → миграция аддитивна, существующие данные не ломает. ⚠️ `dotnet ef` на Linux
капризен (см. memory env-quirks) — генерацию миграции делать по проверенному рецепту.

*Бэкенд. Контракт-тесты на сериализацию DTO + тест edit-сервиса на сохранение/чтение раскладки.*

## 5. Вид «План» + редактор (кусок B2)

- **«Сетка»** рисует плитки **по `PosX/PosY`**, когда раскладка задана; **фолбэк** на текущий поток
  по `SortOrder`, если координат нет (старые клубы не ломаются).
- **«План»** = режим-редактор: **интерактивная изометрическая 2D-карта зала** (не плоский top-down
  грид) — камера с панорамой/зумом, места как объёмные «столы», **перегородки/стены**, **кастомная
  расстановка** (ПК в VIP-комнате, лаунж и т.п.), drag для расстановки и перетаскивания. Палитра
  (хосты по типам / зоны / стены) + инспектор выбранного элемента (тип/поворот/привязка к зоне; для
  зоны — имя/цвет/тип). Сохранение через расширенный edit-эндпоинт (B1). *3D-изо — это слой
  рендера/камеры поверх той же модели B1 (`PosX/PosY/Rotation/SeatType` + геометрия зон + стены);
  модель данных от выбора камеры не меняется. Полноценный 3D — не сейчас, цель — «изо-ощущение».*
- В обычной «Сетке» места **сгруппированы по залам** (заголовок зоны + счётчик) — дешёвая читаемость
  до появления редактора; работает без координат.
- **Право доступа:** редактор за правом управления раскладкой (по контракту роле-видимости —
  `branch_manager`). Точный ключ права свериться с `PermissionCatalog.cs` / `operatorPermissions.ts`
  на этапе плана (не выдумывать — #37).
- Пустое состояние: раскладки нет → холст с приглашением расставить (`EmptyState`).
- Большой зал = скролл холста; 0…500+ мест — оба валидны.

*Фронт + использует B1. Тесты на рендер «Сетки» по координатам и на фолбэк без раскладки.*

## Принцип на масштаб (#28)

Раскладка **опциональна**: 0 мест, место без координат, 500 мест, юникод-имена зон, отсутствующая
геометрия — все валидны. «Сетка» деградирует в поток по порядку, «План» — в пустой холст с
приглашением. Никаких допущений «есть нормальные N мест с координатами».

## Вне объёма (явно)

- **Массовое выделение** (Shift/Ctrl/рамка → массовые действия) — отдельный кусок позже, когда
  появится бэкенд под массовые действия (уведомления/питание); сейчас нёс бы только массовый lock.
- **Бэкенд-фичи** штраф / уведомление игрока / питание сверх lock / пересадка между залами — в меню
  только честные заглушки «скоро»; сами фичи — соседние продуктовые эпики.
- **Бронь с Карты** — это Этап 4 «Брони».
