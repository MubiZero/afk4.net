# Оператор — единая админка: закрытие паритета `/club`

**Дата:** 2026-07-28

**Эпик:** «Оператор = единая админка», расширение под-проекта №3

**Ветка:** `feat/operator-unified-admin-merge-duplicates`

**Основание:** поэкранный аудит Clients, Monetization, Settings и Venue после исходного №3

## 1. Проблема и решение

Исходный №3 закрыл отчёты и аудит, но финальная проверка обнаружила возможности старого
`AFK4.Platform.Web /club`, которые ещё не доехали до Operator App. Удалять `/club` в таком состоянии
нельзя: часть операций исчезнет, а сохранение сотрудника с несколькими ролями способно молча удалить
его дополнительные роли.

Выбран калиброванный parity-пакет: не переносить старый UI и не расширять эпик до полного редизайна,
а встроить недостающие операции в действующие Operator-поверхности. Backend endpoints и доменные
правила переиспользуются; новые серверные обходы не создаются.

## 2. Границы

### В объёме

1. Multi-role приглашение и редактирование сотрудников без потери существующих ролей.
2. Корректный lifecycle клиента при сочетании `isActive=false` и долга.
3. Корректировки `package_time` и `bonus_time`, информативный ledger и частичный возврат.
4. Просмотр пакетов клиента и фактическая продажа пакета через кассовый workflow.
5. Выбор существующей категории товара при создании и редактировании.
6. Честные loading/error-состояния monetization-данных без подмены ошибки пустым списком.
7. Переименование и удаление устройства с причиной и подтверждением.
8. Точечная типизация DTO/request на изменяемых границах.
9. Повторный аудит и сертификат паритета перед под-проектом №4.

### Вне объёма

- device approval, pending approve/reject и `requireManualDeviceApproval`;
- drag-and-drop/bulk floor-map editor;
- свободная валюта на каждой сущности: валюта остаётся настройкой филиала;
- массовая перепись всех `Record<string, unknown>`;
- удаление `Platform.Web /club` — это под-проект №4;
- редизайн Operator-разделов, не необходимый для паритета.

## 3. Архитектура по слайсам

### 3.1. Сотрудники: полный набор ролей

`StaffRolesDestination` использует единый список выбранных ролей и для invite, и для edit. UI
показывает checkbox/multi-select на основе существующего каталога ролей. Invite отправляет полный
`roleNames`; edit начинает с полного массива сотрудника и сохраняет полный массив, а не первую роль.
Пустой набор запрещён до HTTP-вызова.

Текущий пользователь определяется по `session.staffUserId`: действие деактивации для собственной
строки скрывается или блокируется до confirm. Серверная авторизация остаётся обязательной.

### 3.2. Клиенты: состояние, корректировки и возвраты

Read-model клиента хранит `isActive` отдельно от display-status. Долг остаётся финансовым сигналом,
но не заменяет lifecycle-состояние. Деактивированный клиент с долгом показывает оба факта, не
предлагает money-actions и сохраняет доступное действие реактивации.

`CorrectionModal` поддерживает `wallet`, `debt`, `package_time`, `bonus_time`. Денежные счета
отправляют minor units, временные — целые минуты, преобразованные в `quantitySeconds`; несовместимые
поля обнуляются на API-границе. Ledger показывает account type и ненулевое `quantitySeconds`.

`RefundModal` получает редактируемую положительную сумму, ограниченную исходной абсолютной суммой.
Причина обязательна. Reversal-записи по-прежнему не возвращаются повторно.

### 3.3. Пакеты клиента и Касса

Карточка клиента показывает все приобретённые пакеты: название, included/bonus остаток, срок и
активность. Это read-only контекст; продажа не дублируется в drawer.

Продажа пакета живёт в Кассе рядом с выбором клиента. После выбора клиента Operator загружает
доступные package options, проверяет `packages.view`/`packages.purchase`, показывает цену и состав,
и вызывает существующий `purchasePackage` с новым idempotency key. Critical action ждёт backend
confirmation; optimistic финансового результата нет. Успех обновляет клиентский balance/package
context, ошибка сохраняет выбор и показывает конкретную безопасную причину.

### 3.4. Товары и категории

Из каталога строится стабильный список уникальных `{ categoryId, label }`. Если имени категории нет,
используется честный fallback `Категория <short-id>`; фиктивное имя не записывается в backend.

Create-flow позволяет либо выбрать существующую категорию, либо явно создать новую. Новая категория
создаётся только при выбранном режиме «Новая категория». Edit-flow показывает текущую категорию и
позволяет выбрать другую; PATCH получает выбранный `categoryId`.

Загрузка catalog, tariffs и packages не маскирует сетевую ошибку `[]`. Минимум packages получает
собственное error-состояние и retry; успешные соседние данные не объявляются пустыми из-за чужой
ошибки.

### 3.5. Жизненный цикл устройства

В `DevicesTab` под правом `devices.seat_assignment.assign` добавляется изменение display name через
существующий `/api/devices/{id}/rename`. Под правом `devices.credentials.revoke` добавляется удаление
через `/remove`: обязательная причина, отдельное destructive confirmation, ожидание backend и reload.
Активная сессия и остальные запреты остаются серверными конфликтами и выводятся оператору без
обхода. Transport-клиент получает точные request-типы для обеих команд.

## 4. Ошибки и безопасность

- UI-gate всегда дублируется проверкой permission непосредственно перед mutation.
- Backend остаётся источником истины для authorization, active-session guards, финансов и ролей.
- Ошибка загрузки не превращается в пустые настоящие данные.
- Финансовые и package-команды ждут подтверждения backend и используют idempotency key.
- Destructive device removal требует причины и второго явного подтверждения.
- Мутации не теряют уже загруженные роли, категории или lifecycle-флаги.

## 5. TDD и проверка

Каждый слайс начинается с regression-теста, который падает на текущем коде:

- invite/edit сохраняют несколько ролей; self-deactivation недоступна;
- inactive+debt остаётся неактивным и реактивируется;
- time correction формирует секунды, partial refund ограничен исходной суммой;
- пакет реально покупается из Кассы и обновляет контекст;
- existing category не создаётся повторно и меняется при edit;
- packages load failure не выглядит пустым списком;
- rename/remove device идут по точным routes, permissions и confirmation.

После слайсов запускаются focused tests, полный `bun test`, отдельный `bun test src/App.test.tsx`,
`bun run build`, i18n parity guard и повторный статический аудит. Итоговый сертификат перечисляет
каждую возможность `/club`, её Operator-путь и сознательные descope. Только зелёный сертификат
разблокирует планирование №4.

## 6. Definition of Done

- все обязательные расхождения из аудита закрыты или явно подтверждены как descope;
- multi-role и inactive+debt больше не допускают потерю состояния;
- package purchase существует в реальном Operator UI;
- категории товаров переиспользуются и меняются без дубликатов;
- lifecycle устройства покрывает rename/remove;
- focused и полные frontend-гейты зелёные;
- создан и закоммичен сертификат паритета;
- `Platform.Web /club` ещё не удалён.
