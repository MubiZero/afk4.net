# Operator «Касса» (Этап 2) — дизайн раздела

**Дата:** 2026-06-24
**Статус:** утверждён (brainstorming), готов к плану реализации
**Контекст программы:** Этап 2 редизайна Operator.App. Предыдущие этапы (0 Фундамент, 1 Карта, 3 Клиенты, 4 Брони) закрыты. См. `2026-06-22-operator-clients-overhaul-design.md` — этот раздел повторяет его паттерн (единый раздел: якорь-шапка + вкладки + единый дизайн-стандарт).

## Проблема

«Касса» сегодня — не раздел, а зонтик-группа в рельсе из 4 пунктов, плюс «Смены» отдельно в «Отчётах». Кассовые функции распылены:

- **Продажи** (`pos`, `BackendPosWorkspace.tsx` ~1111 строк) — полноценный POS: каталог/категории, корзина, оплата cash·card·deposit, чеки, привязка к игроку/смене.
- **Заказы** (`shop_orders`, `ShopOrdersWorkspace.tsx`) — обработка заказов магазина.
- **Платежи** (`payments`, `BackendPaymentsWorkspace.tsx`) — сюда **спрятаны операции смены**: `openShift`, `recordCashMovement`, `closeShift` + UI «Сверка кассы».
- **Проверка** (`review`, `ReviewWorkspace.tsx`) — аппрув money-actions (refund/correction).
- **Смены** (`shifts`, `ShiftsWorkspace.tsx` ~108 строк) — **только просмотр** выручки/истории; живёт в группе «Отчёты», не умеет открывать/закрывать смену.

Кассир не видит статус смены из любого места; операции смены не там, где их ищут; «единого раздела» нет.

## Цель и объём

Собрать кассовое в **один связный раздел «Касса»** (как собрали Клиентов), навести единый дизайн-стандарт и **закрыть ключевые функц-дыры**. Объём согласован: «реорг + закрыть ключевые дыры» (не полный овэрхол с новыми бэк-фичами вроде банк-инкассации/номиналов).

## Решение: IA (информационная архитектура)

**Меню:** группа `cashier` (4 пункта) + `shifts` (из «Отчётов») → **один пункт «Касса»**. Рельс ужимается. Права по-прежнему скрывают/глушат отдельные вкладки.

**Шапка-якорь `CashShiftHeader`** (паттерн `.booking-header`) — всегда видна над вкладками, показывает **статус смены**:
- Смена закрыта: «Смена не открыта» + кнопка **Открыть смену**.
- Смена открыта: «Открыта · {кассир} с {время} · в кассе {cash} · выручка {revenue}» + кнопки **Внести / Изъять**, **X-отчёт**, **Закрыть смену**.
- Статус кассы виден из любой вкладки — «командная строка» кассира.

**Под-вкладки (3):**

| Вкладка | Содержимое | Источник |
|---|---|---|
| **Продажи** | POS (каталог/корзина/оплата/чеки) + обработка заказов магазина как под-режим | `BackendPosWorkspace` + `ShopOrdersWorkspace` (слияние) |
| **Смена** | открытие/закрытие, внести/изъять, сверка наличных, выручка смены, Z-сводка | собрать из `payments` (shift-ops) + `shifts` (revenue view) |
| **Журнал кассы** | приходно-расходные операции (cash-movements) + аппрув возвратов/коррекций | `ReviewWorkspace` + лента cash-movements |

Смена становится **контекстом** всего раздела (через шапку), а не прячется в «Платежах». POS остаётся главной вкладкой (частотность).

## Достройка «ключевых дыр» — преимущественно фронт поверх готового бэка

Бэкенд почти весь готов; большинство дыр закрывается UI поверх существующих эндпоинтов, **без новых миграций**:

1. **Открыть/закрыть смену из раздела** — `POST /api/branches/{branchId}/shifts/open`, `POST /api/shifts/{shiftId}/close` уже есть → выносятся в шапку-якорь + `PanelModal`.
2. **Приходный/расходный ордер (внести/изъять)** — `POST /api/shifts/{shiftId}/cash-movements` (cash_in/cash_out) есть → модалки из шапки + лента в «Журнале кассы».
3. **Z-сводка при закрытии** — `close` возвращает пересчёт (starting/expected/counted/difference) + выручку → печатная/просматриваемая Z-форма из этих данных (механизм печати чеков уже есть). **Новой сущности Z-отчёта не заводим** (YAGNI; Z = презентация результата закрытия).
4. **X-отчёт (промежуточный, без закрытия)** — `GET /api/branches/{branchId}/shifts/revenue/current` есть → та же форма read-only по кнопке в шапке.
5. **Сверка наличных** — `close` уже считает expected vs counted + tolerance + обязательный manager sign-off при превышении; UI частично в «Платежах» → переносится и полируется.

**Money-path не трогаем** — бэк-операции денег готовы и протестированы.

## Дизайн-стандарт и переиспользование

- Токены `@afk4/tokens` (введены в эпике Клиентов): шкала `--space-1..6`, высоты `--control-sm/md/lg`; контролы 36px, единая сетка.
- Примитивы: `PanelModal` (открыть/закрыть/внести/изъять/X/Z), Toast/Skeleton/EmptyState.
- Новый компонент `CashShiftHeader` (якорь по образцу `.booking-header`).
- Деньги: minor units в DTO → `formatCurrency`/`minorToMajor` на UI-границе (инвариант проекта).
- i18n: новая группа `op.cash.*` (сейчас 0 ключей), переиспуем `op.pos.*` (151) и `op.shifts.*` (17); каждый новый ключ — реально в ru/en/tg (tg — настоящий таджикский), регенерация `messages.ts`.

## Слайсинг (каждый слайс = свой PR, по образцу Клиентов S0..S3)

- **S0 — каркас IA** (рефактор, ~no-behavior-change): новый воркспейс `cash` (`WorkspaceId` union, `navItems`/`workspaceIds` index-parallel, `workspacePermissionRules`, `WorkspaceRouter`/App render); шапка-якорь `CashShiftHeader` (статус смены, read-only на этом этапе); 3 вкладки переносят существующие воркспейсы «как есть»; группа `cashier` → 1 пункт «Касса»; `shifts` убран из «Отчётов»; dev-mock; токены; перенос существующих тестов.
- **S1 — вкладка «Смена»**: открытие/закрытие/внести-изъять через шапку-якорь + модалки (вынуть из «Платежей»); выручка + сверка наличных в одной вкладке; единый дизайн.
- **S2 — достройка дыр**: приходный/расходный ордер UI + лента в «Журнале кассы»; X-отчёт (read-only из current revenue); Z-сводка при закрытии (печатная форма).
- **S3 — слияние «Продажи»**: объединить POS и обработку заказов в под-режимы одной вкладки; финальный дизайн-проход + полировка.

Порядок гибкий, но **S0 первым обязателен** (каркас). Каждый слайс проходит финальное whole-branch ревью и зелёный CI перед мержем.

## Бэк-факты (карта, проверено 2026-06-23)

- Смены: `ShiftEndpoints.cs` — open (`shifts.open`), current (`shifts.view`), cash-movements (`shifts.cash.manage`), close (`shifts.close`, полный пересчёт + tolerance + manager sign-off), revenue/current и revenue (`reports.view`). Сервис `EfShiftService` (+`IOpenShiftResolver`); `MoneyControlPolicy` для tolerance.
- POS: `PosEndpoints.cs` — sales/payments/refunds/void/catalog/inventory; сервис `EfPosService`. Продажа умеет привязку к смене (`ShiftId`) и открытому табу сессии (`SessionId`).
- Деньги/аппрув: `MoneyActionEndpoints.cs` — money-actions (refund/correction approval-очередь), approve/reject/list; pay-debt. **IsActive-guard на money-path закрыт** (см. эпик Клиентов — guard в 5 per-player эндпоинтах + `EfMoneyActionExecutor`).
- Отчёты: `ReportEndpoints.cs` — shifts/sales/cash-operations/operator-actions/gameplay-time (+CSV-экспорт).
- Сущности: `ShiftEntity` (State, StartingCash/Counted/Expected/Difference, ManagerSignOff), `PosSaleEntity` (+lines), `CashMovementEntity` (cash_in/cash_out), `ReceiptEntity`, `MoneyActionRequestEntity`.
- **Нет на бэке (вне скоупа):** X/Z-отчёты как сущности/операции, инкассация с адресом/банком (моделируется как cash_out), детализация по номиналам.

## Тестирование

- Гейты: `bun test` (фронт subdir + `App.test` отдельным прогоном из-за `mock.module`-утечки), i18n `bun test`, `bun run build` (tsc+vite — ловит type-ошибки), `dotnet test` (Platform.Api + Shared.Contracts).
- Перенос существующих тестов (`ShiftsWorkspace.test`, `ShopOrdersWorkspace.test`, `posAvailableInShell.test`) под новую IA.
- Операции смены критичны (деньги) — закрытие/сверку тестировать тщательно; money-path бэка не меняем.

## Риски

- `BackendPosWorkspace.tsx` 1111 строк без собственного теста (лишь косвенное покрытие) — при переносе/слиянии нужен аккуратный smoke; слияние с заказами (S3) — самый рискованный слайс, делать последним.
- Перенос shift-операций из «Платежей»: убедиться, что ничего из «Платежей» не теряется (что там помимо shift-ops — уточнить в плане S1).
- IA-каркас (S0): `workspaceIds`/`navItems` index-parallel — держать массивы синхронными; добавить `WorkspaceId`, `workspacePermissionRules`, render-блок, SummarySidePanel-исключение если нужно.

## YAGNI-срезы (сознательно вне скоупа)

- Новая сущность Z-отчёта (Z = презентация результата `close`).
- Банк-инкассация с адресом/реквизитами (cash_out достаточно).
- Детализация наличных по номиналам.
- Глубокий склад (оприходование/инвентаризация/комбо) — отдельный продуктовый эпик.
