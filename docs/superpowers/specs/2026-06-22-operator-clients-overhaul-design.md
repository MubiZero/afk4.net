# Operator «Клиенты» — овэрхол (Этап 3)

- **Статус:** design (ожидает ревью)
- **Дата:** 2026-06-22
- **Область:** `src/AFK4.Operator.App.Web` (раздел `players`), плюс небольшой кусок `src/AFK4.Platform.Api` + контракты `src/AFK4.Shared.Contracts`.
- **Предшественники:** Этап 1 «Карта» (закрыт), Этап 4 «Брони» (закрыт). Программа этапов: 0 Фундамент → 1 Карта → 2 Касса → **3 Клиенты** → 4 Брони → 5 Отчёты → 6 Управление.

## Контекст

Раздел «Клиенты» (воркспейс `players`) — **не заглушка**, а уже работающий экран `BackendPlayersWorkspace.tsx` (~650 строк): поиск с дебаунсом, сегменты-фильтры, профиль, кошелёк, пакеты, списание долга, создание клиента, бронь из карточки. Есть ~250 i18n-ключей `op.players.*`, CSS (`styles/12-players.css`), API-клиент (`api/clients/players.ts`), контракты на бэке.

Этап 3 — **полный овэрхол**: и редизайн внешнего вида/состояний (как полировали Карту/Брони), и закрытие функциональных дыр, и уборка техдолга раскладки, в одном заходе (нарезано на слайсы).

### Что уже работает

Поиск (дебаунс 180 мс) → `searchPlayers`; per-client `wallet-summary` + `packages`; действия `topUp` / `writeOffDebt` / `buyPackage` / `booking` / `newCard`, все под `hasPermission`.

### Проблемы текущего экрана (чиним независимо от выбора подхода)

1. **История врёт абстракцией** (рабочий стиль #34): показывает сырой `entryType` («top_up») и только 4 записи, хотя `LedgerEntryDto` несёт `Description`, `Reason`, `AccountType`, `QuantitySeconds`, знак суммы.
2. **Пакеты** показывают сырой `state` («active»).
3. **Все формы видны разом** — пополнение/долг/новый-клиент/пакет навалены в одну панель, всегда раскрыты.
4. **Дублирование**: баланс/долг/пакеты — и в полосе метрик, и в профиле; полоса смешивает глобальные и per-client числа.
5. **Монолит** на 650 строк + типы/проекции в общем `operatorHelpers.ts` (в отличие от чистой папки `booking/`).
6. **Слабая типизация** API-клиента: поля читаются через `readString`/`readNumber` из `Record<string, unknown>`.

## Цели / Не-цели

**Цели:**
- Редизайн раздела в master-detail (список + богатая карточка) с состояниями empty/loading/error.
- Закрыть 4 функциональные дыры: богатая история, power-tools (корректировка+возврат), PIN клиента, правка профиля + деактивация.
- Серверная пагинация истории (keyset) + серверный фильтр по типу.
- Уборка: вынос в `src/players/`, типизация API-клиента, заполнение dev-mock.

**Не-цели (вынесено / отложено):**
- Лояльность/бонусы/кешбэк/промокоды/достижения — отдельный продуктовый эпик (см. teardown).
- Начисление бонус-времени через ручную корректировку (часть лояльности).
- Единая база клиентов между клубами (мульти-тенант).
- Сегменты «Новые»/«Спящие» (нет полей `CreatedAtUtc`/последнего визита в результате поиска — не фейкаем).
- Частичный возврат операции (API умеет; оператору сейчас не нужно).

## Решения (зафиксировано)

- **Подход A** — master-detail + drawer/модалки для редкого/чувствительного.
- **4 фичи** — все включены (правка профиля требует нового бэкенд-эндпоинта).
- **YAGNI-срезы:** сегмент «Новые» + расширение `PlayerSearchResultDto`; бонус-минуты в корректировке; частичный возврат; нарядная полоса портфельных метрик.
- **Серверная пагинация истории — добавляем** (слайс S1b). Возвращает «честный» фильтр истории, который иначе был бы бессмысленным над снимком `RecentEntries`.

## Раскладка и IA (Подход A)

```
┌──────────────────────────────────────────────────────────────┐
│ Клиенты            [статус загрузки]        [+ Новый клиент]   │  шапка
├───────────────┬──────────────────────────────────────────────┤
│ ПОИСК         │  ┌─ШАПКА КАРТОЧКИ──────────────────[⋯ меню]─┐ │
│ [сегменты]    │  │ ◯ИО  Имя · телефон · статус               │ │
│               │  │ чипы: Баланс  Долг(красн)  Пакеты         │ │
│ ▸ клиент      │  └───────────────────────────────────────────┘ │
│ ▸ клиент ◀sel │  [ Кошелёк ] [ Пакеты ] [ История ]   табы   │
│ ▸ клиент      │  ───────────────────────────────────────────  │
│ ...           │  контент активной секции                       │
└───────────────┴──────────────────────────────────────────────┘
```

**Слева — список:**
- Поиск (дебаунс, как сейчас).
- Сегменты-чипы (честные, по реальным полям): **Все / VIP / С долгом / Неактивные**.
- Строки: статус-бейдж, имя, телефон, баланс, индикатор долга.
- Состояния: Skeleton при загрузке, EmptyState при пустом результате/без подключения.

**Справа — карточка клиента:**
- Шапка: аватар-инициалы, имя, телефон, статус-бейдж, источник; чипы Баланс / Долг (красный при >0) / Пакеты; меню `⋯` (Править профиль · PIN · Деактивировать/Активировать).
- 3 секции-таба:
  - **Кошелёк:** крупно баланс/долг + инлайн-формы Пополнить / Погасить долг (раздельно) + ссылка «Ручная корректировка» (drawer).
  - **Пакеты:** активные пакеты с человекочитаемым остатком/бонусом/сроком + покупка инлайн.
  - **История:** журнал ledger (источник — новый paged-эндпоинт), фильтр-чипы по типу, человекочитаемый тип + описание + причина + сумма со знаком/цветом + дата; «Показать ещё». На не-реверс-записях — действие «Вернуть».

**Drawer/модалки** (паттерн `BookingDrawer`/`PanelModal`): Править профиль · PIN · Деактивировать (confirm) · Ручная корректировка · Возврат (confirm со строки истории).

Полоса перестаёт мешать глобальное с per-client; профиль не дублирует полосу.

## Функциональные добавки (на реальном API)

### 1. Богатая история + серверная пагинация (S1, S1b)

- Рендер полного `LedgerEntryDto`: тип → локализованный лейбл (`op.players.ledger.type.*`), `Description`, `Reason`, знак/цвет суммы, дата.
- **Новый эндпоинт** (keyset, не offset):
  `GET /api/players/{playerAccountId}/ledger?entryType=&accountType=&before=<cursor>&limit=50`
  → `{ entries: LedgerEntryDto[], nextCursor?: string }`.
  - Org-защита и право как у wallet-summary: `LoadPlayerScopedEndpointAsync` + `billing.view`.
  - Курсор = `(CreatedAtUtc, LedgerEntryId)` — стабильно при новых вставках.
  - Фильтр server-side по `entryType`/`accountType`, валидация против `LedgerEntryTypeNames` / `LedgerAccountTypeNames`.
- **Разделение источников** (#34): История-таб берёт список из ledger-эндпоинта (источник правды); `wallet-summary` — только баланс/долг.
- Клиент: `players.getLedger(id, { entryType?, accountType?, cursor?, limit? })`.

### 2. Power-tools (S2)

- **Ручная корректировка** (drawer): `POST /api/players/{id}/ledger/manual-corrections`, `ManualLedgerCorrectionRequest(OrganizationId, AccountType, Amount, QuantitySeconds, Reason, IdempotencyKey)`. Сейчас — **только деньги** (`AccountType` ∈ wallet/debt), `QuantitySeconds=0`; бонус-время не трогаем.
- **Возврат** (confirm со строки истории): `POST /api/players/{id}/ledger/{ledgerEntryId}/refunds`, `RefundLedgerEntryRequest(OrganizationId, LedgerEntryId, Amount, Reason, IdempotencyKey)`. Сумма = полная сумма записи. Доступно только для записей с `ReversesLedgerEntryId == null` (нельзя вернуть реверс).
- Право: подтвердить при реализации (кандидаты: `billing.money_action.approve`, иначе `billing.wallet.top_up`); под `hasPermission`.

### 3. PIN клиента (S2)

- Модалка задать/сбросить PIN (≥4 символов).
- `POST /api/branches/{branchId}/players/{playerAccountId}/pin`, `SetPlayerPinRequest(Pin)`, право `players.create`, org-scoped (эндпоинт уже есть).

### 4. Правка профиля + деактивация (S3) — новый бэкенд

- **Правка:** `PATCH /api/branches/{branchId}/players/{playerAccountId}` — `UpdatePlayerAccountRequest(OrganizationId, DisplayName, PhoneNumber?)`. Зеркалит create: `RequireBranchPermissionAsync(players.create)`, проверка `OrganizationId == StaffContext.OrganizationId`, org-scoped запрос сущности, `WriteAuditAsync`.
- **Деактивация/реактивация:** toggle `IsActive`. **Только soft** — никакого hard-delete (ledger и история обязаны жить). Эндпоинт: `PATCH .../players/{id}` с полем состояния, либо отдельный `POST .../players/{id}/active-state` — выбрать при реализации; то же право/аудит.
- UI: drawer правки (имя/телефон), confirm на деактивацию; деактивированный клиент помечается в списке/карточке, действия с деньгами — заблокированы.

## Архитектура кода (рефактор, S0)

Вынос монолита в `src/players/` (зеркало `booking/`), каждый файл — одна ответственность (#16):

- `playersModel.ts` — типы (`ClientItem`, `LedgerView`, …) + чистые мапперы; забрать `PlayerClientItem`/`projectPlayerClient` из `operatorHelpers.ts`; лейблы типов ledger, логика сегментов; деньги/время остаются в общих хелперах.
- `usePlayers.ts` — загрузка (поиск + кошелёк + пакеты), дебаунс, load-states. *Мягкий кандидат:* если оркестратор после разбивки остаётся простым — грузить инлайн как в `booking/`. Решение в S0.
- Компоненты: `ClientList.tsx`, `ClientDetail.tsx`, `WalletSection.tsx`, `PackagesSection.tsx`, `HistorySection.tsx`, `ClientProfileDrawer.tsx`, `PinDialog.tsx`, `CorrectionDrawer.tsx`.
- `BackendPlayersWorkspace.tsx` → тонкий оркестратор.
- **Типизация** `api/clients/players.ts`: заменить `Record<string, unknown>` на реальные DTO из контрактов (`PlayerSearchResultDto`, `WalletSummaryDto`, `LedgerEntryDto`, `PlayerPackageDto`, …) (#34/#37).

## Права

Воркспейс `players` уже агрегирует права (`players.view`, `players.create`, `billing.view`, `billing.wallet.top_up`, `billing.debt.pay`, `packages.view`, `packages.purchase`). Новые действия:
- Правка/деактивация/PIN → `players.create` (как create).
- Корректировка/возврат → подтвердить точное право при реализации.

## Честные ограничения / отложено

- Серверной «глубокой» истории до S1b нет — до неё фильтр не строим (не фейкаем фильтрацию над снимком).
- Сегменты ограничены реальными полями (нет «Новые»/«Спящие»).
- Бонус-время, лояльность, частичный возврат, кросс-клубная база — вне скоупа (отдельные эпики).
- Точное право для корректировки/возврата — подтвердить при реализации S2.
