# Реворк склада оператора → раздел «Склад» (секция рейла)

**Дата:** 2026-06-25
**Статус:** дизайн утверждён, ждёт ревью spec → план
**Контекст эпика:** Operator redesign. Касса (Этап 2) закрыта; склад был вкладкой Кассы. Этот документ выносит склад в отдельный корневой раздел и достраивает складской слой, который на бэке наполовину готов, но на фронте оператора недоступен.

---

## 1. Проблема

Текущая вкладка `Касса → Склад` (`CashStockWorkspace.tsx`) умеет ровно две вещи: показать остатки и списать товар (форма «товар + кол-во + причина» → `adjustment` с `-qty`). Половина складского слоя простаивает:

- **Движения** (`StockMovementEntity`) бывают 4 типов — `purchase` / `sale` / `refund` / `adjustment`. Фронт умеет создавать только `adjustment`-минус: **приёмку поставки оператор сделать не может**.
- **Журнал движений** (`GetStockMovementsAsync`) бэк отдаёт, фронт **не показывает** — нет прослеживаемости «откуда взялось / куда делось».
- **Себестоимость** (`UnitCostMinorUnits`) есть в каждом движении, но при списании фронт всегда шлёт `0` — стоимость остатков и убыток нигде не считаются.
- **Порог низкого остатка у каждого товара свой** (`PosProductEntity.ReorderThreshold`, уже в `PosProductDto`), а фронт **захардкодил `LOW_STOCK_THRESHOLD = 2`** для всех — нарушение «конкретика на руках не доезжает».
- Каталог-настройка и складские движения **смешаны** в `Управление → Товары` (`SettingsGoodsSection.tsx`): там и создание товаров, и форма движений, и история.
- **Штрих-кодов нет вообще** — ни в модели товара, ни в POS.

«Массивный реворк» — это поднять весь складской слой и развести ответственность, а не дорисовать кнопок.

---

## 2. Решения и допущения

**Расположение:** Склад → **отдельная секция рейла** (новый корневой раздел рядом с Касса / Отчёты / Управление). Товары и остатки живут вне открытой смены (поставка приходит до смены, инвентаризация — ночью), поэтому натягивать их на вкладку Кассы тесно.

**Скоуп:** приёмка · журнал движений · инвентаризация · аналитика/себестоимость · штрих-коды (сквозная вертикаль).

**Утверждённые допущения:**
- **Себестоимость — средневзвешенная скользящая (moving average).** При каждом приходе пересчитывается средняя цена единицы. Стоимость остатка = остаток × средняя; маржа = (цена продажи − средняя себестоимость) / цена. Проще FIFO, не требует хранить партии.
- **Без справочника поставщиков (YAGNI).** При приёмке поставщик и № накладной — опциональные текстовые поля на документе, не отдельная сущность.
- **Сканер — USB-HID-клавиатура.** Сканер «печатает» цифры штриха + Enter. Фронт ловит быстрый ввод символов с финальным Enter; спец-API/драйвера не нужно, работает в WebView2-хосте. Архитектура ввода расширяемая под камеру в будущем (не сейчас).
- **Несколько штрихов на товар.** У одного SKU бывает несколько EAN (разные партии/поставщики + внутренний). Коллекция штрихов → любой пикается в тот же товар.
- **Сканер в приёмке/POS:** пик того же товара = **+1 к количеству** существующей строки (накопление), а не новая строка.
- **Себестоимость в приёмке** подставляется из прошлой закупочной автоматически, оператор может поправить.

## 3. Архитектура раздела

Раздел `Склад` = **4 вкладки** (под-навигация `cash-tabs`-стиль) + **правая context-zone** (3-я колонка shell, «Сводка склада»):

| Вкладка | Назначение |
|---|---|
| **Остатки** | главный экран: список товаров с реальным per-product порогом, себестоимостью, маржой, стоимостью остатка, статусом; поиск; фильтры (Все / На исходе / Нет); действия `＋`приёмка / `−`списание на строке |
| **Приёмка** | оприходовать завоз: сканер/поиск → строки прихода (товар, кол-во, себестоимость) → провести; накладная справа |
| **Журнал** | лента всех движений с фильтром по типу; кто/когда/что/почём; экспорт CSV |
| **Инвентаризация** | пересчёт по факту (сканер) → расхождения → корректировки на разницу |

**Context-zone (правая колонка)** меняется по вкладке:
- Остатки → «Сводка склада»: стоимость склада + разбивка по категориям, блок «Заказать» (на исходе/нет → кнопка «Оформить приёмку»), движение за смену.
- Приёмка → «Накладная» (поставщик / № / дата) + итог приёмки + «Провести».
- Журнал → период (Смена / Сегодня / 7 дней) + итог за период.
- Инвентаризация → прогресс пересчёта + итог расхождений + «Провести инвентаризацию».

**Разведение ответственности (важно):**
- `Управление → Товары` (`SettingsGoodsSection`) остаётся **только каталог-настройкой**: категория, название, SKU, цена, отслеживать остаток, разрешить отрицательный, доступен в shell, **порог заказа** (вынести в форму — поле есть в DTO), **штрих-коды** (новая секция).
- **Складская часть** (форма движений + история) из `SettingsGoodsSection` **переезжает** в раздел Склад (Приёмка/Журнал). Дубль устраняется.
- Вкладка `Склад` **убирается из Кассы**; вкладки Кассы → `Продажи / Смена / Журнал`.

## 4. Экраны (ключевые элементы; мокапы — в `.superpowers/brainstorm/`)

**Остатки.** Список `cash-stock-row`: иконка · имя+SKU+категория · [плотная группа числовых справа: Остаток · Порог · Себест. · Цена · Маржа · Стоимость остатка] · действия. Статус кодируется цветом (норма/на исходе=янтарь/нет=красный) по per-product порогу. KPI — компактно в context-zone, не громоздкими карточками.

**Приёмка.** Сканер-полоса сверху (фокус-ловушка HID, мигающий курсор) + «Добавить вручную». Строки прихода: товар+штрих, степпер кол-ва, поле себестоимости (преподставлено), сумма, удалить. Только что отсканированная позиция подсвечена. Проведение → `purchase`-движения (+кол-во, себестоимость) по строкам.

**Журнал.** Лента: время · тип-чип (Приход/Продажа/Списание/Возврат/Коррекция) · товар+контекст (чек/брак/инвентаризация/поставщик) · ±кол-во · сумма по себест. · кто. Цвет: приход зелёный `+`, продажа нейтральный `−`, списание/коррекция янтарь.

**Инвентаризация.** Сканер ведёт пересчёт. Строки: товар · учётный · факт (input/сканер) · расхождение (само считается) · сумма по себест. Недостача янтарь, излишек зелёный, совпало «0», непересчитанные тусклые. Проведение → по `adjustment` на каждую разницу, ложатся в Журнал с пометкой «инвентаризация».

**POS-сканер (Касса → Продажи).** Бейдж «Сканер активен» (пульс) в шапке каталога. Пик штриха → lookup по штриху → товар в чек (подсветка строки + тост). Повторный пик = +1. Неизвестный штрих → тост «штрих не привязан». Поиск-поле принимает и текст, и скан.

**Карточка товара со штрихами (Управление → Товары).** Форма товара + поле «Порог заказа» + секция «Штрих-коды»: чипы (несколько, первый «основной»), удаление, ручной ввод + кнопка «Отсканировать» (ловит штрих со сканера, привязывает). Правая карточка — превью «как увидит Касса» + экономика товара.

## 5. Дизайн-инварианты (обязательны для всех экранов)

- **Токены `@afk4/tokens`**, тема dark. Палитра нейтрально-серая (`#121212`/`#1e1e1e`/`#242424`).
- **Акцент — emerald `#2cc592`** (`var(--accent)`), НЕ синий. (Прежняя заметка про «синий #1f6feb» была неверна — исправлено.)
- **Деньги — белый моноширинный** (`--font-mono`, `text-strong`). **Янтарь (`--warning`) только для предупреждений** (низкий остаток / недостача), не для сумм. Красный — «нет в наличии» / опасные действия.
- **Per-product порог** (`ReorderThreshold`), НЕ хардкод. `0` = без алертинга.
- **Контраст таблиц (читаемость):** числовые значения — `text-primary` (яркие, полужирные); заголовки колонок и SKU — минимум `text-tertiary` (не `quaternary`); границы строк — `border-default`. Применить ко всем таблицам склада.
- Числовые колонки — плотной группой справа, моноширинные, right-aligned; имя тянется слева.
- Реальные классы оболочки: `operator-shell` (rail 74 / center / context 260–304), `cash-head`, `cash-tabs`, `cash-stock-row`, `pos-*`, `settings-*`.

## 6. Модель данных и контракты

### 6.1 Новое — штрих-коды (миграция)
`ProductBarcodeEntity`: `BarcodeId`, `OrganizationId`, `BranchId`, `ProductId` (FK), `Code` (string), `IsPrimary` (bool), `CreatedAtUtc`.
- Уникальность `Code` в пределах `(OrganizationId, BranchId)` — один штрих не может указывать на два товара.
- `PosProductDto` дополняется `Barcodes: string[]` (или список объектов с `IsPrimary`).
- Эндпоинты: CRUD штрихов товара (`POST/DELETE /api/branches/{branchId}/inventory/products/{productId}/barcodes`); **lookup по штриху** для POS/приёмки (`GET /api/branches/{branchId}/inventory/products/by-barcode/{code}` → товар или 404).
- IDOR-guard через `StaffContext.OrganizationId` (паттерн org-эндпоинтов).

### 6.2 Средневзвешенная себестоимость
Нужна для стоимости остатка и маржи. Два варианта (решить в плане):
- **(а) Хранить** `AvgCostMinorUnits` на `PosProductEntity`, пересчитывать при каждом `purchase` (`newAvg = (oldQty*oldAvg + inQty*inCost)/(oldQty+inQty)`). Дёшево читать, нужна миграция + аккуратный пересчёт.
- **(б) Считать на лету** из `purchase`-движений. Без миграции, дороже на чтение.
**Рекомендация:** (а) — раздел Остатки читает среднюю на каждый рендер списка.
`PosProductDto` дополняется `AvgCostMinorUnits` (+ опц. `MarginPercent` вычисляемо на UI).

### 6.3 Уже есть, переиспользуем
- `StockMovementEntity` (4 типа), `GetStockMovementsAsync(productId?, limit)`, `CreateStockMovementAsync`, `GetCatalogAsync` (отдаёт `StockOnHand`, `ReorderThreshold`, `AvailableInShell`).
- **Приёмка** = пакет `CreateStockMovement(purchase, +qty, unitCost)` по строкам (идемпотентность на каждую строку). Рассмотреть batch-эндпоинт vs N вызовов.
- **Инвентаризация** = набор `adjustment` на разницу `(факт − учётный)` с `reason="инвентаризация"`. Рассмотреть batch.
- **Списание** = `adjustment` с `-qty` (как сейчас), но себестоимость берётся из средней (для учёта убытка), не `0`.

### 6.4 Money-path guard
Складские движения меняют только количество/себестоимость, не баланс игрока — но проверить, не задевают ли money-action политику. Приёмка/инвентаризация — операторские, под `manageInventoryStock` permission (уже есть).

## 8. Тестирование

- **Фронт:** `bun test` (happy-dom + jest-dom). Smoke на каждый экран (рендер, пустые/loading/error состояния), guard на per-product порог (не хардкод), guard на `useBarcodeScanner` (накопление +1, Enter-терминатор, дебаунс быстрого ввода).
- **i18n:** используемые `t()`-ключи существуют в каталоге (key-existence guard, как PR #115); новые ru-ключи реально переведены на tg (анти `tg===ru` guard).
- **Бэк:** `dotnet test` — штрих-уникальность (один код ≠ два товара), lookup, средневзвешенная себестоимость (пересчёт при приходе), приёмка/инвентаризация создают правильные движения, IDOR-guard по `OrganizationId`.
- **Контраст:** значения чисел/заголовков не на `quaternary` (визуальный инвариант; по возможности — lint/тест на токены).
- **Дизайн под масштаб:** 0 товаров, длинные названия, юникод, отрицательная маржа, штрих 13+ цифр.

## 9. Отложено / Open questions

- **Камера-сканер** — архитектуру ввода делаем расширяемой, но реализуем только USB-HID.
- **Справочник поставщиков** — пока текстовое поле; сущность Supplier — будущий бэклог.
- **Аналитика-отчёты** (оборачиваемость, залёживается, ABC) — KPI-сводка в S0 даёт базу; глубокая аналитика → возможно раздел Отчёты, не Склад.
- **Batch-эндпоинты** приёмки/инвентаризации vs N идемпотентных вызовов — решить в плане S1/S4.
- **Хранить vs считать** среднюю себестоимость — рекомендация «хранить», финал в S0.
- **Кто видит маржу/себестоимость** — оператор или только owner? Уточнить permission-видимость экономических колонок.
