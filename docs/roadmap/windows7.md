# Windows 7 на ПК клуба

Последнее обновление 2026-11-04.

## Зачем

Почти половина ПК в клубах Таджикистана — Windows 7, в том числе 32-битная. Это и игровые ПК (CS 1.5/1.6, Quake,
Dota 1), и ПК администратора. .NET 10 и свежий WebView2 на Windows 7 не запускаются.

Решение владельца (2026-10-29): AFK4 остаётся на .NET 10, сервер на .NET, экраны на WebView2, код открытый. XP не
поддерживается.

Решение владельца (2026-11-04), после проб ниже: программы на ПК собираются **Native AOT**, экраны показывает **Miniblink** — один файл машинного кода
без .NET, одна сборка на Windows 7–11 (x86 и x64). Путь через .NET Framework 4.8 (раздел «Как устроено») остаётся,
пока AOT не принят на стендах, потом удаляется.

## План перевода на AOT

Каждый шаг — отдельный PR; анализатор AOT (`IsAotCompatible`) включается в проекте вместе с переводом и ломает сборку
на любое новое предупреждение.

1. **Агент:** JSON через генератор (`JsonSerializerContext`, умолчания Web), настройки — генератор привязки,
   WMI — WmiLight (вшит), TLS 1.2 на Windows 7 у HTTP и SignalR, публикация `PublishAot` для win-x64 и win-x86.
2. **Общее окно `AFK4.WebHost`:** окно Win32 + Miniblink (решение владельца 2026-11-04, итоги пробы ниже) вместо WPF и
   WebView2. Свои файлы экранов через перехват сети (`mbOnLoadUrlBegin` + `mbNetSetData`), чужие адреса запрещены,
   мост `window.afk4Host` ↔ `mbOnJsQuery`, масштаб Windows, русские даты и числа.
3. **Мост экранов:** модуль хоста каждого экрана берёт `window.afk4Host`, а не `chrome.webview` — в Miniblink
   `window.chrome` неизменяем.
4. **Мастер установки**, затем **экран игрока** (киоск, оверлей, полоса обслуживания — окна Win32) и **Панель** — на
   `AFK4.WebHost`, JSON через генератор.
5. **Установщик и обновления:** пакеты AOT для x64 и x86 с `mb132_x64.dll` / `mb132_x32.dll`; WebView2 больше не нужен.
6. Приёмка на стендах Windows 7 x86/x64 и Windows 11, затем удаление net48.

## Как устроено

| | Windows 10 и 11 | Windows 7 SP1 (x64 и x86) |
|---|---|---|
| Платформа программ | .NET 10, своя копия в установщике | .NET Framework 4.8, докачивается, если её нет |
| Экраны (игрок, Панель, мастер) | WebView2 из Windows или из установщика | WebView2 109, последний для Windows 7, докачивается |
| WebView2 SDK в сборке | 1.0.4314 | 1.0.1518, новее не запускается на Windows 7 |
| Сеть | система выбирает TLS 1.2/1.3 | программа сама просит TLS 1.2 (`UseTls12OnWindows7`) |
| Канал команд (SignalR) | WebSocket | Windows 7 в .NET Framework не умеет клиентский WebSocket — SignalR сам переходит на SSE |

Код один. Каждая программа на ПК (агент, экран игрока, Панель, мастер) и их общие библиотеки (контракты,
ядро мастера, локализация) собираются в два варианта: `net10.0`/`net10.0-windows` и `net48`. Сервер и тесты остаются
на .NET 10.

Недостающее в 4.8 закрывают:
- **Пакет Polyfill** — заплатки на уровне исходников, в программу не попадают отдельной библиотекой.
- **`src/Compat/`**:
  - ключи P-256 в PEM и PKCS#8 байт в байт как у .NET 10;
  - `NativeLibrary`;
  - канал со списком доступа;
  - код ответа у `HttpRequestException`;
  - `string.Create` и `Replace` с учётом регистра.
- **`DateOnly`/`TimeOnly`** в контрактах — с тем же JSON, что у .NET 10.
- **Brotli** частей дельта-обновлений — BrotliSharpLib.
- **Пояса IANA** («Asia/Dushanbe») — TimeZoneConverter.

Проверка: `tests/AFK4.NetFramework.Tests` (net48, только на Windows; задача CI «Build And Test Windows») сверяет
это с эталонами, снятыми с настоящего .NET 10.

## Ход работ

1. **Сделано** (ветка `feat/netfx48`): все программы на ПК собираются под net48; тесты совместимости; сборка
   установщика явно берёт .NET 10.
2. Сборка net48-вариантов в CI: x64 и x86, пакеты для докачки.
3. Установщик: бандл (Burn — родной код, работает на Windows 7) смотрит версию Windows и разрядность. На Windows 7
   он докачивает с `updates.afk4.net`:
   - .NET Framework 4.8 — только если её нет;
   - WebView2 109 нужной разрядности;
   - net48-сборки программ.

   На Windows 7 без обновления KB4474419 (подписи SHA-2) .NET 4.8 не ставится — установщик скажет об этом.
4. Обновления дельтой по варианту: сервер знает платформу и разрядность ПК из сердцебиения и отдаёт свой манифест.
5. Стенды Windows 7 x64 и x86 (образы — от владельца, `~/VMs/iso`), приёмка всех сценариев.

## Проба Native AOT (2026-10-29, ветка `probe/aot`)

Вместо .NET 4.8 — .NET 10 Native AOT: программа собирается в один файл машинного кода без рантайма. Окна — простое
окно Windows с WebView2 через WebView2Aot (MIT), без WPF. Сборка — только на Windows (workflow `AOT Probe`).

| | x64 | x86 |
|---|---|---|
| Агент-проба: служба, HTTPS, WMI (WmiLight, вшит), JSON контрактов (генератор), P-256, канал со списком доступа, SignalR | 9,4 МБ | 8,0 МБ |
| Окно-проба: WebView2, экран входа, мост `postMessage` ↔ C# | 4,4 МБ | 3,9 МБ |

Windows 11 (стенд UTM): агент в консоли и службой — 7/7 проверок; окно в 64 и 32 бита — страница и мост работают,
37 МБ памяти у процесса окна. Для сравнения сейчас: агент 83 МБ, окно 146 МБ.

Грабли пробы:
- WmiLight по умолчанию кладёт `WmiLight.Native.dll` рядом — `PublishWmiLightStaticallyLinked=true` вшивает его.
- Строки в WebView2 передавать обёртками библиотеки (`NavigateToString(string)`), а не `PWSTR.From` + `Dispose`:
  иначе повреждение кучи (0xc0000374).
- Канал без буфера: запись ждёт читателя.

Windows 7 SP1 Ultimate x86 и x64 (сборка владельца, стенды UTM, 2026-11-04):
- агент в консоли и службой — 7/7 проверок на обеих разрядностях, без .NET на машине;
- окно на WebView2 109.0.1518.140 — страница, мост `postMessage` ↔ C# работают на обеих разрядностях;
  у процесса окна 10–12 МБ, у процессов WebView2 вместе ~190 МБ.

Грабли Windows 7:
- TLS 1.2 у клиента выключен по умолчанию, HTTPS к Cloudflare падает (`net_http_ssl_connection_failed`). Программа
  просит TLS 1.2 сама: `SocketsHttpHandler.SslOptions.EnabledSslProtocols = Tls12` на Windows старше 8, и тот же
  обработчик — в SignalR (`HttpMessageHandlerFactory`). Реестр клуба не трогаем.
- Нынешний загрузчик WebView2 (`MicrosoftEdgeWebview2Setup.exe`) на Windows 7 не запускается: `0x8007007F` за 2 с.
- WebView2 109 есть в каталоге Microsoft Update («Microsoft Edge-WebView2 Runtime Version 109 Update», 132 МБ x86,
  144 МБ x64). Это пакет EdgeUpdate: с `/silent /install` он зависает, без аргументов — тоже. Работает то, что лежит
  внутри (`MicrosoftEdge_X86_109.0.1518.140.exe`, подпись Microsoft):
  `--msedgewebview --verbose-logging --do-not-launch-msedge --system-level`, 20–30 с. Его и докачивать на Windows 7.
- Значка «⌫» нет в шрифтах Windows 7 — на экране квадрат. Иконки на экранах — SVG, не символы шрифта.

## Проба Servo вместо WebView2 (2026-11-04)

Servo nightly от 2026-11-03 (`servoshell`, только x86_64): в архиве 99 МБ, распакованный — 289 МБ (сам `servoshell.exe` —
109 МБ, остальное — GStreamer и ffmpeg). Открывал демо: Панель (https://demo.afk4.net/) и экран игрока (`/shell/`).

| | Servo | Edge (Chromium, как WebView2) |
|---|---|---|
| Панель на React 19 | рисуется, нажатия и переходы работают | работает |
| Память, Панель (личная, все процессы) | 464 МБ, один процесс | 169 МБ, 7 процессов |
| Память, экран игрока | 336 МБ | 183 МБ, 8 процессов |
| Размер у нас | ~100 МБ в установщике | 0 на Windows 10/11 (уже в системе) |
| Windows 7 x64 | не запускается: `0xC0000139` (нет функции Windows) | WebView2 109 работает |
| Windows 7 x86 | сборки нет | WebView2 109 работает |

Встраивание — только из Rust: готового C API нет. Итог: Servo не легче WebView2 ни по памяти, ни по размеру и не
работает на Windows 7. Остаёмся на WebView2 (на Windows 7 — 109), программы — Native AOT.

## Проба Miniblink вместо WebView2 (2026-11-04, ветка `probe/aot`, `probes/aot/BlinkProbe`)

Miniblink (github.com/weolar/miniblink49, Apache-2.0) — Chromium 132 (выпуск 2025-12-12), ужатый в одну DLL с C API.
Проба — .NET 10 AOT, 1,3–1,6 МБ, открывает демо и сама проверяет мост страница ↔ C# (`mbQuery`).

| | Miniblink 132 | WebView2 / Chromium |
|---|---|---|
| Движок в установщике | одна DLL: x86 54 МБ (24 МБ в zip), x64 66 МБ (27 МБ) | 0 на Windows 10/11; Windows 7 — WebView2 109, 132–144 МБ |
| Windows 7 x86 | экран игрока работает | WebView2 109 работает |
| Windows 11 x64 | Панель работает: нажатия, касса, корзина | работает |
| Память, экран игрока (Windows 7 x86) | 28–30 МБ личной, ~80 МБ рабочей, один процесс | ~190 МБ, 6 процессов (WebView2 109) |
| Память, Панель (Windows 11) | 83 МБ личной, один процесс | 169 МБ, 7 процессов (Edge) |
| Мост | `window.mbQuery` ↔ `mbOnJsQuery`/`mbResponseQuery` | `chrome.webview` |

Найдено:
- `window.chrome` в Miniblink — неизменяемый геттер, каждый раз новый объект: подставить `chrome.webview` нельзя. Мост
  экранов нужно брать через своё имя (по одному модулю хоста на экран), остальной React не меняется. Проба проверила
  весь экран игрока, заменив `window.chrome` в скриптах на лету.
- Масштаб Windows: без `mbEnableHighDPISupport()` (только после `mbInit`) страница рисуется в 100% и нажатия мимо; с ним
  вёрстка шире окна — размер окна под масштаб ещё не подобран.
- `Intl` знает только `en` (`supportedLocalesOf` → `en`): дата «M11 6, Fri», числа «1,480.5». Правила множественного
  числа есть. Решение — полифилы FormatJS с данными ru/tg/en: включаются, только если движок не умеет язык, код
  форматирования экранов не меняется. `navigator.language` в Miniblink — `zh-CN`, меняется `mbSetLanguage`.
- После жёсткого выключения Windows 7 Miniblink падал на старте (`c0000005` в `mb132_x32.dll`), после штатной
  перезагрузки — нет. Причина не найдена.
- Синхронный JS в `mbOnDidCreateScriptContext` роняет процесс; скрипт в страницу — через перехват ответа
  (`mbNetHookRequest` + `mbNetSetData`), как и раздача своих файлов.
- Лицензия: репозиторий Apache-2.0, у бинарных выпусков 132 отдельных условий не нашлось. Сборки делает один автор;
  Chromium 132 больше не обновляется — годится только для своих страниц с запретом чужой навигации.

## Мастер установки на AOT + Miniblink (2026-11-05, PR «AFK4.WebHost»)

Мастер — один файл: 8,4 МБ x64, 7,0 МБ x86 (было ~147 МБ с .NET и WPF), рядом `mb132_x64.dll` / `mb132_x32.dll`.
Приёмка: Windows 11 (стенд ARM), Windows 7 SP1 x86 и x64 — экран, окно без рамки (развернуть, вернуть, рабочая
область), тема сохраняется между запусками, ввод с клавиатуры без щелчков, вход через мост → HTTPS (на Windows 7 —
TLS 1.2) → ответ сервера на экране. Память всего мастера с движком: 29 МБ (Windows 7 x86), 70 МБ (Windows 11).

Грабли `AFK4.WebHost`:
- Свои файлы отдаются из `mbOnLoadUrlBegin`; тип файла (`mbNetSetMIMEType` и заголовок `Content-Type`) — **после**
  `mbNetSetData`, иначе тип пустой и модульные скрипты Vite отвергаются.
- `mbOnLoadUrlBegin`, `mbOnNavigation` Miniblink зовёт из своего потока, не из потока окна.
- Фокус клавиатуры — окну движка (`SetFocus(mbGetHostHWND)`), иначе набранное до первого щелчка пропадает.
- Минимальный размер окна — не больше рабочей области (800×600 и 1024×768).

## Русские даты и числа в Miniblink (2026-11-05)

`loadIntlPolyfills()` из `@afk4/formatting/intl-polyfills` — первым делом в мастере, экране игрока и Панели. Если
`Intl` не знает ru, en или en-GB, ставит полифилы FormatJS (PluralRules, NumberFormat, DateTimeFormat с данными ru, en,
en-GB и основными поясами, среди них Asia/Dushanbe) и передаёт им пояс ПК — сами они считают в UTC. Браузеры и WebView2
ничего не качают: проверка добавляет к экрану 3,6 КБ, полифилы — отдельные файлы (~1,3 МБ, 0,3 МБ сжатыми; из них пояса
0,8 МБ). Тест `intlPolyfills.test.ts` урезает `Intl` до `en`, как в Miniblink, и сравнивает даты и суммы с родными.

## Токен в запросах экрана и ссылки наружу (2026-11-05)

Экран игрока ходит на сервер сам (`fetch`), а токен знает только программа: WebView2 ставит заголовок в
`WebResourceRequested`. В `AFK4.WebHost` то же делает `RequestAuthorization` — из `mbOnLoadUrlBegin` через
`mbNetSetHTTPHeaderField`. `OpenExternalLinks = false` — ссылки https:// и tg:// с экрана не открываются в браузере ПК.
Проба на Windows 7 SP1 x86 (мастер AOT со страницей пробы): токен уходит в `fetch` GET, в POST с JSON (с предварительным
запросом CORS) и в XHR к своему адресу, к чужому — нет; `window.open` → `null`, ссылки https:// и tg:// не открылись,
страница осталась на месте.

## Окно киоска в AFK4.WebHost (2026-11-05)

`WebHostOptions.Kiosk` — окно экрана игрока: на весь монитор поверх панели задач, «поверх всех» с начала, Alt+F4 и
WM_CLOSE не закрывают (закрывает только программа), смена разрешения игрой — снова на весь экран. `SetTopmost` меняет
«поверх всех» без фокуса, `BringToFront` выводит вперёд с фокусом вопреки запрету Windows (подключение ко вводу
переднего окна, иначе нажатие Alt), `Show(activate: false)` — появиться, не выдёргивая игрока из игры, `IsInFront`.
Политика (когда «поверх всех», когда полоса) остаётся в экране игрока, как `ShellWindowPolicy` сейчас.

Проба на Windows 11 (окно-проба .NET 10 x64 с Miniblink, запуск планировщиком при открытом блокноте): окно вышло
вперёд и закрыло весь экран, SC_CLOSE и WM_CLOSE не закрыли, снятое «поверх всех» пропустило блокнот вперёд,
возвращённое не отняло у него фокус, свёрнутое вернулось вперёд с фокусом, закрытие программой завершило процесс.
Смену разрешения на стенде не проверить (UTM) — на живом ПК.

Грабли, найденные пробой (касаются и мастера):
- Miniblink крутит свой цикл сообщений и выбрасывает сообщения потоку: продолжения `await`, посланные
  `PostThreadMessage`, терялись, а WM_QUIT не доходил — процесс висел без окон. Работа для потока окон идёт
  сообщением невидимому окну (`HWND_MESSAGE`), цикл кончается и по закрытию последнего окна. На Windows 7 x86
  закрытие разбирал вложенный цикл Miniblink, пока главный ждал в `GetMessage`, — будит его таймер того же окна.
- Передним окном Windows считает скрытое окно меню Miniblink `_ContextMenu_` — «впереди» проверяется по процессу.
