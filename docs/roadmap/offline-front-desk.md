# Офлайн у стойки

Статус: дизайн, 27.10.2026. Задача из плана пилота (P1, п. 1): при пропавшем интернете кассир сажает гостя
за наличные, продлевает, рассчитывает, продаёт товар и закрывает смену. Когда связь вернётся, всё
досинхронизируется без двойных списаний.

## Что есть сейчас

- **ПК.** Агент держит **уже идущую** сессию до оплаченного конца без сети. Предел — 4 часа по решению
  владельца от 30.09. Аренду (lease) подписывает только сервер: ключ лежит в `Sessions__SigningPrivateKeyPem`,
  агент проверяет подпись публичным ключом, полученным при регистрации.
- **Панель без связи.** Показывает карту из кэша («Офлайн — данные от HH:MM, только просмотр»). В очередь
  ставятся только «запереть» и «открыть» (`actionOutbox.ts`).
  - Кнопки «посадить», «продлить», «рассчитать», «касса» при этом **активны** и падают с сетевой ошибкой.
    Это баг: этап 0.
- **Канала Панель → ПК по локальной сети нет.** Агент слушает только именованные каналы на своей машине.
- **Повторы безопасны.** Сервер принимает ключи повтора (idempotency) у всех денежных и сессионных команд.
  Но время операции ставит сам, в момент прихода запроса: исходное офлайн-время пропало бы.

Вывод: без нового доверенного звена в клубе ПК без интернета не открыть.

## Решение

**Ключ клуба.** На ПК администратора Панель сама создаёт пару ключей ECDSA P-256 для офлайн-аренд.
- Приватный ключ не покидает машину (DPAPI).
- Публичный ключ Панель регистрирует на сервере, пока связь есть.
- Сервер раздаёт его агентам филиала в ответе на сердцебиение. Агент хранит список доверенных офлайн-ключей.

**Офлайн-аренда.** Та же каноническая запись аренды плюс признак «офлайн» и идентификатор ключа. Агент
принимает её, только если:
- подпись верна, а ключ — ключ этого филиала;
- **сам агент не на связи с платформой**: при живой связи распоряжается сервер;
- срок не больше 4 часов, как у офлайн-льготы;
- номер аренды растёт (защита от повтора).

**Канал по локальной сети.** Агент слушает HTTP на одном порту. Правило брандмауэра ставит сам агент: любой профиль
сети (клубная сеть нередко «Общедоступная»), только локальная подсеть (28.10).
- Принимаются только подписанные команды: открыть по офлайн-аренде, продлить, запереть.
- Подпись и есть авторизация: чужой в сети без ключа клуба ничего не откроет.
- Адреса ПК Панель знает из кэша карты. Агент докладывает свой адрес в локальной сети в сердцебиении.

**Журнал кассы.** Каждая офлайн-операция — отдельная запись в журнале на диске ПК администратора, через мост
WPF, не в localStorage. Виды записей: сессия начата, продлена, окончена, продажа, движение наличных, смена.
- У каждой записи есть ключ повтора, исходное время и смена.
- Цены — из кэша тарифов и каталога на момент последней связи. Панель так и пишет: «цены от HH:MM».
- Офлайн — **только наличные и гость**. Кошелёк игрока без сервера не списываем: его баланс знает только
  платформа.

**Досинхронизация.** Новый маршрут сервера принимает журнал по порядку.
- Каждая запись применяется с исходным временем, в смену, которая была открыта, и с тем же ключом повтора.
  Повтор безопасен.
- Деньги записываются как их фактически взяли: офлайн-цену не пересчитываем по новому тарифу.
- Итог — сообщение владельцу в Telegram: «Без связи 2 ч 15 мин: 5 сессий, 340 с. наличными».

**ПК раньше Панели.** Агент вернулся в сеть до того, как Панель отправила журнал. Тогда агент сообщает
серверу о действующей офлайн-аренде. Сервер не запирает такой ПК, пока аренда не кончилась или журнал не
пришёл.

## Товары и смена без связи (27.10.2026)

- **Продажа.** Раздел «Касса» без связи показывает товары из кэша (обновляется раз в 5 минут, пока связь есть;
  скрытые категории не кэшируются) и принимает только наличные. Запись `sale` хранит строки с ценой, по которой
  взяли деньги. Сервер пишет те же строки, что онлайн-продажа: продажа, строки, списание со склада, платёж
  наличными в смену, чек — с временем продажи. Остаток склада не проверяется: товар уже отдан.
- **Закрытие смены.** Кассир пересчитывает ящик вслепую; Панель не показывает ожидаемую сумму. Запись
  `shift_closed` хранит посчитанное. Сервер считает ожидаемое и расхождение по всем деньгам смены, включая
  присланные раньше в том же журнале, и закрывает смену временем из записи. Владелец получает обычные отчёты
  о закрытии и тревогу о расхождении.
- **Расхождение сверх допуска** без связи подписать некому. Смена всё равно закрывается, с пометкой
  `SignOffReason = "offline: closed without connection, no manager sign-off"`. Иначе отказ закрытия отправил бы
  в отказ и следующую смену, и все её деньги.
- **Открытие смены.** Запись `shift_opened` несёт номер новой смены, который придумала Панель, и размен. Следующие
  записи кладут деньги в неё. Сервер откажет (`offline_shift_already_open`), если в филиале уже открыта другая смена.
- **Права** те же, что онлайн, по каждой записи: продажа — `pos.sales.create` и `pos.sales.pay`, открытие —
  `shifts.open`, закрытие — `shifts.close` или `shifts.close_own` для своей смены. Без права запись отклоняется
  (`offline_not_allowed`) и остаётся у сервера.
- **Не сделано:** оплата кошельком игрока и возврат без связи. Закрывает смену на сервере тот, кто досылает
  журнал, а не обязательно тот, кто сдавал смену.

## Риски, которые принимаем

- **Ключ клуба на ПК администратора.** Кто завладеет этой машиной, сможет открывать ПК в зале без денег,
  пока нет интернета, и не дольше 4 часов на аренду. Что смягчает:
  - каждая офлайн-аренда попадает в журнал;
  - расхождение журнала и аренд, о которых доложили агенты, видно владельцу.
- **Два ПК администратора без связи** не видят продаж друг друга. Пилот — один ПК у стойки. Для нескольких
  — следующий этап (журналы по локальной сети).

## Этапы

0. **Честный офлайн в Панели.** Без связи денежные и сессионные действия выключены и объяснены, а не падают.
1. **Агент.** Доверенные офлайн-ключи из сердцебиения, проверка офлайн-аренды, канал в локальной сети,
   правило брандмауэра в MSI.
2. **Хост Панели.** Ключ клуба (создание, DPAPI, регистрация), отправка подписанных команд на ПК, журнал на
   диске.
3. **Панель.** Офлайн-сценарии у стойки: посадить за наличные, продлить, рассчитать, продажа за наличные,
   закрыть и открыть смену (товары и смена — 27.10).
4. **Сервер.** Регистрация ключей, раздача агентам, приём журнала, терпимость к офлайн-аренде, отчёт
   владельцу.
5. **Приёмка на VM** с выдернутой сетью: VM — ПК игрока, Mac — ПК администратора.

## Приёмка на VM, 27.10.2026

Стенд: VM — ПК игрока (агент 0.1.376), Мак — ПК стойки (`~/VMs/afk4-win/lab/desk.cs`: тот же алгоритм подписи,
ключ зарегистрирован в учебном API), учебный API выключен на 2,5 мин.

| Проверка | Итог |
|---|---|
| Офлайн-аренда, пока ПК на связи | отказ «платформа решает» |
| Открыть ПК без интернета (30 мин) | открыт, таймер на экране игрока |
| Продлить (seq 2) | принято, срок +30 мин |
| Повтор старой аренды (seq 1) | отказ |
| Аренда на 5 ч | отказ, предел 4 ч |
| Чужая сессия, пока идёт своя | отказ |
| **«Конец», подписанный чужим ключом** | **был принят и запер ПК гостя** — исправлено в этом PR |
| Связь вернулась при идущей офлайн-сессии | сервер ПК не запер (цикл планировщика прошёл) |
| Досылка журнала (2 сессии, продление, конец) | деньги наличными 15 + 15 + 22,50 с. с исходным временем и в открытую смену; повтор — `duplicate` |
| Онлайн-расчёт офлайн-сессии | доплата 0, ПК заперт |

Не проверено на живом ПК: Панель на Windows как ПК стойки (отправка через мост и журнал на диске) — её путь
покрыт тестами хоста и Панели, но не прогнан вживую.
